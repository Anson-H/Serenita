# Serenita 后端边界审查与封装改进计划

审查日期：2026-09-06。状态：B01–B16 已实施，完整回归与已配置真实服务验收通过，逐项关闭及运行证据见[实施记录](verification/backend-refactor-implementation.md)。下文保留审查时的问题依据和验收要求，其中“本次”指原审查阶段；旧路径和行号仅表示审查时位置，以代码文本记录，不作为当前源码链接。当前职责以 docs/当前执行 为准，实施结果见关联记录。

结论：存在职责交叉、封装不足和可清理的冗余。下文合并为 16 个改进项，其中 13 项涉及职责与依赖，3 项涉及重复实现或无用途入口。优先级表示实施先后，不表示已经发生线上故障。

本次以当前工作区为依据，检查了 backend/app 的 106 个 Python 文件的结构、依赖和引用，并对主要入口、长方法、事务、文件生命周期及模型调用链进行了源码阅读。后端约 3.2 万行，静态识别出 84 个 HTTP 路由声明；检查了 38 个后端测试文件的分布及相关用例，其中共有 491 个测试函数定义。参数化会增加实际用例数，这些数字不代表测试运行或覆盖率。

本次没有修改后端、前端或测试代码，没有执行测试、联网模型调用、数据操作或服务重启。仅新增这份计划。已有验收记录可用来寻找用例，不能替代针对实施基线重新运行的验收。

用户要求的“所有现有功能与服务正常”作为每批修改的完成条件。静态审查不能证明未来实现绝无回归；本计划通过固定外部行为、保持事务和权限边界、分批实施、全量回归及真实服务验收来落实这一要求。证据不足的项不能按完成处理。

## 审查时的现状与处理原则

当前 API → Service → Repository 分层已经存在，通用 Harness、插件工具、统一 Schema 描述、会话事件持久化和文件清理队列也已有实现。改进以现有这些能力为基础。

所有提议都是进程内代码职责调整。HTTP 方法、路径、请求与响应字段、状态码、工具名称与工具参数结构、模型可见描述、技能授权、数据库物理结构、JSONL 格式和现有文件位置均作为保持项。代码移动时直接更新当前调用者，避免保留两套实现、旧入口回退或数据迁移。

同一数据库内或附加数据库上的原有事务必须保留。编号步骤只用于开发实施，不进入医疗业务执行链。模型仍根据技能与工具观测自主选择下一步。

## 发现与具体计划

### B01：会话服务集中承担任务执行、标题任务和流式呈现

证据：`backend/app/application/conversation_service.py:169` 共有约 5,900 行；同一类包含轮次启动与队列、后台线程及租约、标题任务、取消、SSE 重放和列表管理。后台任务从第 818 行开始，标题任务从第 962 行开始，SSE 从第 1447 行开始。现有 conversation_streaming.py 仅封装七行 SSE 编码，主要订阅逻辑仍在服务内。

问题：线程注册、会话操作锁、取消信号和浏览器重放混在同一个对象中。改动任一职责都需要理解其余职责，成员撤权也必须依赖这个大型服务才能中断会话。

计划：先抽出 SSE 订阅与响应投影，再抽出标题任务管理；最后封装轮次任务管理和队列提交。ConversationService 保留会话用例入口，使用明确的协作者完成工作。会话锁和任务注册表统一持有，不能在每个新对象中各建一套。

保持与验收：同会话最多一个执行中轮次；不同会话可独立执行；started/queued 响应、队列顺序、调整方向、取消后的正文、重连事件和手工标题 CAS 均保持。SSE 继续消费持久化事件。重点运行会话并发、取消、列表、成员执行及事件测试。

优先级：高。拆分风险：高，分三批完成。

### B02：会话压缩越过 Harness 和模型网关的封装边界

证据：`backend/app/application/conversation_service.py:2863` 直接调用 runtime._assembly、runtime._model_runtime_context；第 2927、4863 行直接调用 ModelProviderService._transport_request。第 4832 行的压缩方法还负责预算、指纹、模型摘要、检查点和并发复查。第 4316 行以后集中处理模型输入追溯，第 5295 行以后处理模型流和事件写入。

问题：会话服务必须掌握 Harness 如何重新生成提示词、模型网关怎样转换文本工具协议，才能正确估算和压缩上下文。这是明确的私有实现依赖。

计划：由 Harness 提供公开的请求重建能力；模型网关提供公开的传输请求准备能力；应用层独立封装压缩协调和模型调用审计。预算算法仍归通用运行时，检查点提交归持久化协作接口。分别移动后更新唯一调用链，不同时改写压缩算法。

保持与验收：实际发送 payload 与审计 payload 同源；输入追溯路径精确覆盖；二进制和凭证脱敏；原生及文本工具协议的预算一致；当前用户输入、未决工具结果、来源保留效果和已读取技能恢复不丢失；压缩无进展时的失败行为保持；取消或撤权后禁止继续调用模型。

优先级：高。拆分风险：高。

### B03：会话 Repository 同时负责多个存储生命周期

证据：`backend/app/repositories/conversation_repository.py:333` 约 2,240 行，既拥有会话与轮次 SQL，也负责 JSONL 事件及索引协调、分支创建、附件命名、文件实际写入和过期恢复。第 1514 行处理写入中附件恢复，第 1584 行处理附件文件创建。

问题：数据库索引、事件文件和附件文件具有不同失败与恢复条件，都集中在同一类。单纯移动 SQL 会把现有提交与补偿关系拆散。

计划：封装会话索引、轮次索引、附件存储三个内部能力；保留一个明确的会话持久化协调入口来处理 JSONL 与索引的先后提交和恢复。附件写入必须整体包含名称预留、独占创建、刷盘、ready 标记及失败清理。

保持与验收：事件提交成功但索引提交失败时可恢复且不重复启动；分支种子及资源引用保持；文件名规范化、大小写碰撞、不可复用名称、附件 TTL、写入中恢复及共享文件引用计数保持；跨进程竞争仍只有一个有效写入者。

优先级：高。拆分风险：高。

### B04：事件领域、模型历史与界面投影的职责集中

证据：`backend/app/conversation_projection.py:88` 同时提供模型历史装配、技能可见性、界面记录投影、增量投影和响应序列化，共约 1,240 行。`backend/app/session_events.py:404` 同时维护事件格式校验和恢复收尾规则。

问题：压缩历史的语义调整、页面新增展示字段和 JSONL 格式检查会接触同一组大型文件，容易误把页面投影当成模型历史依据。

计划：分离模型历史与技能可见性投影、时间线记录投影、HTTP/SSE 响应投影；保持单一时间线记录投影供详情和 SSE 使用。事件类型与格式校验继续拥有唯一契约，恢复规则通过独立纯函数消费它。

保持与验收：记录标识与顺序、增量和完整投影的一致性、编辑与重新生成后的线性历史、分支前缀、注释选区、原始工具请求字符串、Token 汇总和引用来源保持。不能为详情与 SSE 各写一套相同投影。

优先级：中。拆分风险：中高，与 B01、B02 配合。

### B05：报告服务混合领域操作、文件处理与模型输入呈现

证据：`backend/app/application/report_service.py:110` 约 1,570 行。第 135 行处理完整解析校验结果，第 409 行构造会话输入，第 789 行上传来源，第 1126 行调用外部程序生成缩略图，第 1273 行以后处理来源复制、哈希和清理。

问题：报告事实修改和缩略图渲染依赖同一大类。公共分类校验 semantic_lab_category 也定义在该文件，被账号设置服务引用。

计划：提取报告结构与分类校验、报告读取投影、来源存储、缩略图渲染；保留 ReportService 作为有成员授权的领域用例入口。模型附件渲染和报告缩略图只共享底层文件处理能力，各自保留完整读取和首页预览要求。

保持与验收：五类医疗报告、手工创建、批量字段修改、添加与删除检验指标、重分类、解读结果及过期状态保持；校验仍只读；来源验证、首个主要来源、重分类后稳定 report_id、上传失败清理保持。首屏缩略图不能代替模型读取完整 PDF。

优先级：中。拆分风险：中高。

### B06：检验指标分类目录与报告持久化缺少清晰的内部封装

证据：`backend/app/repositories/report_repository.py:1639` 约 3,537 行，分类目录的读取、版本、名称冲突、影响统计、重分类与合并集中在第 1639–2826 行；第 2462 行的合并在同一连接和事务内联动报告记录。

问题：账号级分类目录操作和成员级报告操作混合在一个 Repository；名称规则、联动判断与 SQL 交织。二者存在真实的事务内依赖，不能各自开事务后顺序调用。

计划：封装分类目录读写及报告事实读写，以显式事务对象共享同一连接；只把无数据库依赖的规则提取为纯函数。跨目录与报告的操作仍由一个事务入口完成，报告失效标记、空报告删除、来源清理任务在原事务内提交。

保持与验收：主分类及相关分类、别名冲突、目录版本冲突、合并冲突、授权访问时可做的别名补充、联动统计保持；任何一步失败全部撤销该次未提交变更。普通报告页面字段编辑继续采用最后有效写入优先，不能引入目录版本令牌。

优先级：高。拆分风险：高。

### B07：物理 Schema 与业务模型的归属不一致

证据：`backend/app/model_capabilities.py:110` 同时定义能力对象、两张 SQLite 表、SQL 生成、存储编码和响应；报告与会话 Schema 分别定义在 Repository 文件顶部，而其他数据库在 storage 下。

问题：使用一个模型能力对象会连带依赖 SQLite 的物理结构；存储定义的查找位置不统一。当前并非同一张表存在两处定义，本项解决的是归属问题。

计划：将模型表定义归入配置数据库的存储定义，将报告与会话数据库定义归入对应存储模块；能力对象与业务归一化独立，行编码及解码归持久化边界。每张表继续只有一处 Python 定义。

保持与验收：移动前后生成的表、列顺序、主外键、索引与检查规则完全相同；已有非空库校验失败时继续拒绝且不修改数据。此项不需要改库或迁移。

优先级：中。拆分风险：中。

### B08：成员 Repository 直接拥有会话和收藏的引用 SQL

证据：`backend/app/repositories/member_repository.py:92` 知道 conversations、favorites 的表名、标识列和具体 UPDATE 语句；第 621 行开始的成员删除同时协调授权、偏好、成员库与其他数据存储。静态依赖存在 MemberRepository 与 ConversationRepository 相互引用，部分通过局部 import 实现。

问题：修改会话或收藏存储需要同步了解成员 Repository 内的 SQL；已有 MemberDataStoreParticipant 对成员领域库提供注册边界，但操作者私有引用还没有同等封装。

计划：为会话、收藏的成员引用读取与解除关联提供窄接口，具体 SQL 归各自存储模块；成员删除协调器传入原事务连接和数据库别名。沿用显式参与方注册，不通过扫描目录发现业务库。成员 Service 依赖窄的会话中断接口。

保持与验收：成员删除、撤权、历史可读、名称呈现、引用置空、偏好替换、访问版本更新和执行中断保持。任何附加数据库校验或修改失败，都必须使成员删除事务整体失败；来源文件仍在提交后按持久化清理任务删除。

优先级：高。拆分风险：高。

### B09：构造依赖与成员作用域依赖隐式全局环境

证据：`backend/app/repositories/member_repository.py:54` 每次创建默认 MemberRepository；ReportService.for_member 同样自行创建默认对象，而 ReportService 又允许单独传入 paths。ConversationRepository 接受 persistence，却直接使用全局 app_paths。报告授权装饰器在调用中修改 service.account_id 和 repository.account_id。

问题：传入的存储对象与后续权限复查可能来自不同的依赖来源。实际风险在自定义数据根、测试隔离和拆分后对象复用中更明显；本次没有认定默认开发环境已经发生跨账号访问。

计划：在应用装配位置明确传入路径、Repository、访问检查器和任务管理器；作用域对象只表达可信身份与访问条件，使用同一访问检查器做实时复核。取消调用中改写 Repository 账号的方式，明确对象按账号或成员的生命周期。

保持与验收：增加显式 AppPaths 与全局 DATA_ROOT 不同的隔离用例；覆盖同进程两套存储、同账号不同成员、授权变更后复查、嵌套授权读取及并发删除。保持 ContextVar 支持的重入语义和锁顺序，不能将权限检查降为构造时检查一次。

优先级：高。拆分风险：高。

### B10：模型 Provider 基类承担过多独立能力

证据：`backend/app/providers/base.py:204` 文件约 1,997 行，混合连接测试、模型列表、媒体探测、思考模式识别、HTTP 传输、取消、错误分类、流解析与消息编码。能力探测从第 322 行开始，传输从第 747 行开始。

问题：仅调整探测规则也需接触实际对话传输的基类，供应商子类还依赖基类文件中的内部帮助函数。

计划：提取传输、流解析、能力探测、错误解析及消息编码协作者；Provider 只组合这些能力并声明供应商差异。当前 urllib 和可取消 httpx 两条路径先按现有语义封装，不借机统一重试策略。探测任务注册与删除时取消归应用层的模型探测管理器。

保持与验收：三家模型供应商的请求字段、原生附件上限、媒体探测资产、思考模式和元数据合并保持；覆盖首字节前取消、流中取消、无超时模式、代理环境、上游 4xx/5xx、上下文溢出以及模型删除后的禁止回写。真实请求次数也作为验收项。

优先级：高。拆分风险：高。

### B11：模型配置 Service 依赖 SQL 参数位置和存储编码

证据：`backend/app/repositories/model_provider_repository.py:9` 的读写接口多使用 values 元组；`backend/app/application/model_settings_service.py:276` 直接装配 SQL 字段顺序，并调用 capability_column_values 生成存储值。

问题：SQL 虽已移出 Service，但参数顺序和存储编码仍向上泄露。新增列或调整 SQL 容易造成不同层之间的位置错配。

计划：Repository 使用有名字的参数或明确的写入对象，内部完成 SQL 顺序和编码；事务对象仍明确暴露可组合操作。配置 Service 保留字段更新语义、能力规则和默认用途判断。

保持与验收：省略、空值、清空和保留旧值的差异保持；密钥留空保留规则、模型 ID、四类默认用途、删除后的外键清空、能力识别回写条件保持。

优先级：中。拆分风险：中。

### B12：报告插件注册入口同时承担可信来源解析和写入适配

证据：`backend/app/plugins/report/registry.py:38` 包含 RuntimeReportService 的约 140 行逻辑，通过 __getattr__、getattr 和参数字典 pop 连接工具与 ReportService。`backend/app/plugins/report/tools/base.py:8` 的大部分方法使用宽泛的参数字典。

问题：插件注册、可信完整解析校验结果的解析、来源再次核对和业务写入适配混合。接口没有清楚表达哪些参数来自模型、哪些来自当前会话和工具观测。

计划：将可信工具观测解析和报告运行时适配移到独立组件，registry 仅组装和注册；为导入、查询、修改分别定义实际需要的接口与可信输入对象，取消宽泛属性转发。仍由单个工具主动调用一个领域能力。

保持与验收：完整解析校验结果必须来自当前可见线性会话；来源哈希及来源原文再次核验；伪造账号、成员、会话和索引均拒绝；只读账号不能写入；工具观测解码和已执行结果的可追溯性保持。不得将适配器扩展为固定导入工作流。

优先级：中。拆分风险：中高。

### B13：领域错误的归属仍使 API 依赖具体 Repository

证据：`backend/app/api/account_settings.py:19` 直接导入四种 ReportRepository 异常并在第 77 行映射；`backend/app/application/favorite_service.py:244` 将 sqlite3.IntegrityError 转为重复收藏。成员错误帮助函数也定义在 Repository 模块中，被上层广泛引用。

问题：领域失败类型与某个存储类绑定，替换内部存储组织会连带改变 HTTP 适配层；存储异常与领域冲突没有统一的窄边界。

计划：将跨层使用的领域异常移到对应领域错误模块；Repository 精确识别可预期的约束冲突；Service 输出稳定领域错误；API 继续负责 HTTP 映射。保留实际错误，不将未知异常全部当成用户输入错误。

保持与验收：状态码、code、message、details 及冲突附加字段保持；覆盖重复收藏、目录名称冲突、目录版本冲突、合并冲突和非业务数据库故障。不能只验证“抛出了异常”。

## 本次不列为必须修改的问题

1. API 中的请求模型、Cookie、下载响应和流式上传读取属于 HTTP 职责。字段模型放在 API 或 schemas 的位置差异，单凭命名不足以成立为问题。
2. API 提前限制上传体积、Service 再检查文件和数量，各有保护作用。不能只为去重而删除任意一层。
3. Schema 校验、事务约束、实时权限复查、重复调用保护、资源预算和持久化清理任务属于允许的确定性边界，应保留。
4. 模型能力汇总与分思考状态能力承担不同用途；模型原生附件与 PDF 渲染读取也有不同要求，不能合成一个简单布尔值或统一白名单。
5. API 手工报告创建与智能体创建入口、单项与批量更新有明确使用场景，不能仅因名称相近而删除。
6. Web 配置与搜索读取集中在约 466 行的服务内有继续分离的空间，但当前尚未发现足以单独要求拆分的具体损害。可在将来有独立变更需要时处理，本次不为凑数量增加改造项。
7. 模型和联网密钥使用不同主密钥、AAD 与密封前缀，这是有意义的安全隔离。共用加密底层不等于合并这两种凭证。
8. 报告与 Web 引用转换分别面向报告保存和会话导出，失败规则不同。通用会话导出直接引用 Web 导出帮助函数目前不足以证明业务固定编排。
9. 当前主路径仍通过动态 Harness 调用工具。没有将上述职责问题解释为需要重写医疗业务流程，也没有发现应以微服务替代现有分层单体的依据。
