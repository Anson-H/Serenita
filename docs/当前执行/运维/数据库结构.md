本文是当前物理 SQLite Schema 及其跨存储引用的唯一文档入口。代码中的唯一结构声明由 `backend/app/storage/schema.py` 提供统一表达和校验能力，各数据库所有者模块只声明自己的表契约，不再分别维护列集合、键集合和散落的建表 SQL。

## 统一表达规则

### 数据库文件名

数据库文件名使用小写 `snake_case`，并以 `.db` 结尾。名称直接表达数据库负责的领域，不添加 `info`、`data` 或 `storage` 等泛化后缀。当前数据库统一使用 `auth.db`、`settings.db`、`favorites.db`、`members.db`、`conversations.db`、`reports.db`、`medical_logs.db` 、`medications.db`、`body_metrics.db`、`notifications.db`、`background_tasks.db` 和 `member_lifecycle.db`。

### 表名

表名使用小写 `snake_case`。对象或记录集合使用复数名，例如 `accounts`、`login_sessions`、`web_providers`、`conversations`和 `report_sources`。关系记录使用能直接说明关系的复数名，通用关联表以 `_links` 结尾。固定设置表以 `_settings` 结尾，文件清理发件箱以 `_cleanup_outbox` 结尾。一对一的医疗报告类型附属表使用单数 `_report` 名称。显式索引名包含所属表的完整当前名称；表名调整时同步更新外键目标和显式索引。

### 字段顺序

每张表的物理字段顺序固定按以下分组排列；同组字段再按领域读取顺序排列：

1. 主键字段：必须位于最前，复合主键字段连续出现并与主键顺序一致。
2. 作用域字段：例如非主键的 `account_id`、`member_id`。
3. 引用字段：保存其它记录标识及其类型判别值、但不属于作用域的字段。
4. 业务数据字段：名称、正文、路径、能力数据等主体内容。
5. 状态字段：状态、布尔标记、计数、过期时间和状态更新时间。
6. 审计字段：放在最后；同时存在时 `created_at` 先于 `updated_at`。

多个表保存同一种数据时，共用字段使用相同的字段名、列定义、用途用语和组内相对顺序。共用文件元数据按 `mime_type` → `size_bytes` → `relative_path` → `sha256` 排列，分别表示“MIME 类型”“文件字节数”“相对路径”和“文件 SHA-256”；会话与医疗报告文件路径相对账号目录，用药原件路径相对账号的 `medications/files/` 目录。会话附件与用药原件在这些字段之前保存 `original_filename`（原始显示文件名）；医疗报告来源的文件名从 `relative_path` 提取，不单独存储。记录创建时间统一使用 `created_at`；只有时间表达独立领域事件时才使用对应事件名称。

列定义内部固定使用“存储类型 → `COLLATE` → `NOT NULL` → `DEFAULT`”的顺序。主键、外键、唯一限制和检查规则统一放在字段之后，不给这些规则附加名字。下列表格的“列定义”只描述字段自身，表格后直接给出 SQLite 规则。

`member_id` 始终标识成员。对象自身使用“成员 ID”，其它记录按关系使用“所属成员 ID”“关联成员 ID”或“被授权成员 ID”；健康档案是该成员的数据范围，不另设档案标识。

### 主键选择

统一风格表示相同的数据采用相同的判断规则，不表示所有表必须使用相同数量的主键字段：

- 一行是一个可以独立识别的对象时，使用一个稳定标识作为主键。账号或成员等归属字段不因为权限检查而自动加入主键。
- 一行只表达两个对象之间的关系时，使用关系两端的标识组成主键。这样直接禁止同一关系重复，不额外制造无用途的行号。
- 一行只在父对象内部成立，并且它的明细标识允许在不同父对象中重复时，使用父对象标识与明细标识组成主键。
- 一张表与父表一对一时，直接复用父表主键；固定设置使用只能取固定值的单例标识。

当前表的主键选择示例及健康日记、用药记录表的完整归类如下：

| 情况      | 表与主键                                                                                                                                                                                                                                                                                                                                                                                                                                                           | 直接原因                                      |
| ------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------- |
| 独立对象    | `accounts(account_id)`、`login_sessions(session_token_hash)`、`member_ownerships(member_id)`、`model_providers(provider_id)`、`models(model_id)`、`web_providers(provider_id)`、`favorites(favorite_id)`、`members(member_id)`、`conversations(session_id)`、`conversation_resource_cleanup_outbox(cleanup_id)`、`reports(report_id)`、`report_sources(resource_id)`、`report_source_file_cleanup_outbox(cleanup_id)`、`lab_items(item_id)`、`lab_categories(category_name)` | 一行本身就是一个账号、会话、文件、任务、医疗报告或目录项，一个字段已经可以准确找到它。 |
| 固定设置    | `model_access_settings(singleton_id)`、`member_preferences(singleton_id)`、`conversation_preferences(singleton_id)`、`web_access_settings(singleton_id)`                                                                                                                                                                                                                                                                                                          | 整张表只能有一条设置。                               |
| 对象关系    | `member_grants(member_id, account_id)`、`report_source_links(report_id, resource_id)`、`lab_item_category_links(item_id, category_name)`                                                                                                                                                                                                                                                                                                                         | 一行表示两个现有对象之间的一条关系。                        |
| 父对象内的明细 | `conversation_turns(session_id, turn_id)`、`conversation_resources(session_id, resource_id)`、`lab_test_report(report_id, item_id)`                                                                                                                                                                                                                                                                                                                              | 轮次和资源按聊天保存，检验项目按医疗报告保存；同一个明细标识可以出现在不同父对象中。  |
| 一对一附属数据 | `examination_report(report_id)`、`pathology_report(report_id)`、`surgery_report(report_id)`、`other_report(report_id)`                                                                                                                                                                                                                                                                                                                                            | 每份对应类型的主医疗报告最多只有一行附属内容，`report_id` 已经唯一。    |

健康日记与用药记录采用同一套主键选择规则：

| 情况      | 表与主键                                                                                                                                                                                                                                                             | 直接原因                            |
| ------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------- |
| 独立对象    | `medical_logs(medical_log_id)`、`medications(medication_id)`、`medication_plans(medication_plan_id)`、`medication_inventory(medication_batch_id)`、`medication_sources(resource_id)`、`medication_source_cleanup_outbox(cleanup_id)`、`notifications(notification_id)` | 每条日记、药品、计划、批次、原件、清理任务、通知都能独立定位。 |
| 父对象内的明细 | `medication_requests(actor_account_id, request_id)`                                                                                                                                                                                                              | 写入请求按操作者及其请求标识去重。               |
| 固定设置    | `account_preferences(singleton_id)`                                                                                                                                                                                                                              | 操作者账号只有一份统一通知设置，固定标识为 `1`。      |

组合外键与组合主键不是一回事。例如医疗报告附属表使用 `(report_id, member_id)` 外键，是为了阻止成员不一致；其主键仍然只需 `report_id`。同理，接口地址同时包含父对象与明细标识，主要用于归属和权限检查，也不自动决定数据库主键。

### 约束与索引格式

每张表列出其专属数据库规则；下述字段内容规则由共享 Column 定义为各表生成，并与专属规则一同创建和检查。建表规则固定按 `PRIMARY KEY`、`FOREIGN KEY`、`UNIQUE`、`CHECK` 排列；索引使用完整的 `CREATE INDEX` 或 `CREATE UNIQUE INDEX`。索引名只需是合法 SQLite 标识，并且在同一个数据库中不重复，不要求固定前缀。

- 外键始终显式写出 `ON UPDATE` 和 `ON DELETE`；`NO ACTION` 不再省略。
- 同一个 `.db` 文件内可由 SQLite 强制的关系使用外键。跨数据库、JSONL、文件系统或允许目标先删除的关系集中列在下文[跨存储引用](#跨存储引用)中，不生成外键、触发器或其它伪数据库对象。
- 应用连接统一执行 `PRAGMA foreign_keys = ON`。
- 主键和 `UNIQUE` 生成的 SQLite 自动索引不重复列出；文档中的 `CREATE INDEX` 只列代码单独创建的索引。
- 当前 Schema 不定义视图或触发器。

## 字段内容与条件必填

数据库与应用层共同拒绝缺少必填内容的写入。共享 Column 定义为必填 TEXT、可空的主键／作用域／引用／状态／审计 TEXT 生成非空白 CHECK；空白范围与 Python `str.strip()` 一致，包含空格、制表符、换行和全角空格。可空字段允许 SQL NULL；非空字段同时使用 NOT NULL。主键、文件路径、名称、哈希和审计时间均受此规则保护。

明确允许空字符串的字段只有：`reports.analysis_content`（尚未解读）、`body_records.metric`（非测量记录）、`favorites.source_session_id`（收藏医疗报告）、两张通知表的 `message`（内容由关联资源提供）。可空的普通说明文本继续遵循各自领域契约。

- 所有 BLOB 内容必须是非零长度的二进制值；凭证未配置时允许 NULL。
- `lab_items.aliases`、`favorites.tags` 为有效 JSON 数组，空数组合法。身体记录的 `payload`、导入任务的 `payload`、用药计划的 `schedule`、模型的 `capability_profiles`、`capability_detection`、`embedding_capabilities` 为有效 JSON 对象；可空对象允许 SQL NULL，不接受 JSON null 或空字符串。身体记录的 `source_payload` 接受有效 JSON 对象或数组，以保留单条及合并来源材料。`thinking_modes` 保存非空的换行分隔文本。
- `medications.generic_name` 必填。处方类型、计划开始／结束精度、使用状态与创建请求操作采用限定值；库存数量为 1 至 120 字符的非负普通十进制文本，零合法。
- `medication_plans.ends_at` 是具体结束时间时 `end_precision` 必填；未知或 long_term 时精度为 NULL。暂停、停用、完成的计划不能保存排程。
- `medication_requests.operation` 为 batch 或 plan 时 `member_id` 必填。
- `body_records.kind` 为 measurement 时 `metric` 不得为空白；睡眠、运动和 payload 中 precision 不是 instant 的区间记录必须有 `ends_at`。
- `reports.analysis_content` 有内容时 `analysis_updated_at` 必填。既往史任一项有内容时，对应 `*_updated_at` 必填；清空既往史后可以保留更新时间。
- `conversation_turns.user_message_id`、`stream_id` 必填；失败状态必须有 `error_code` 与 `error_message`。
- 收藏消息时 `favorites.source_session_id` 不得为空白。成员删除后收藏的 `member_id` 仍允许清空。
- 当前通知类型限定为 medication_due、medication_expired、answer_completed，均必须保存 `resource_type`、`resource_id`、`validity_key`；前两种同时要求 `member_id`，回答完成通知允许账号作用域。
- 通知开关启用时间、待关联附件过期时间、中断会话任务的会话标识继续按现有条件要求填写，并拒绝空白。

应用层通过参数结构、Service 校验及 Repository 写入前的共享 `Table.validate_values` 检查内容与条件；SQLite CHECK 独立保护直接 SQL INSERT 和 UPDATE。该检查只处理数据一致性，不安排智能体业务动作。字段后的规则顺序仍为 PRIMARY KEY、FOREIGN KEY、UNIQUE、CHECK。

## 跨存储引用

本节集中维护 SQLite 字段或数据库路径与其它数据库、JSONL 和文件的准确对应关系。本文把字段直接保存的身份目标称为“引用”，把通过 `member_ownerships.account_id` 定位并检查健康档案所有者账号的成员资料行的步骤称为“跨库一致性校验”。`PRAGMA foreign_key_check` 只检查同一个数据库中的真实外键，不能检查以下关系。每项同时说明当前代码维护关系的位置和目标失效后的处理；业务授权、页面行为和文件生命周期仍由链接的领域或存储文档说明。

### 跨数据库引用

#### 账号私有数据库与账号身份

`serenita_files/accounts/{account_id}/` 下的 `settings.db`、`favorites.db`、`members.db`、`conversations.db`、`reports.db`、`medical_logs.db` 和 `medications.db` 都引用 `auth.db.accounts.account_id`。目录中的 `account_id` 就是私有数据库的账号作用域，私有表不重复保存该字段；用药写入请求的 `actor_account_id` 另行标识发起操作的账号。认证与路径组件只接受规范账号 ID；注册在认证库事务中创建当前配置库入口。认证记录存在但账号目录或必需配置库缺失时返回数据缺失错误。

#### 成员登记、资料与选择

`members.db.members.member_id` 与 `auth.db.member_ownerships.member_id` 一一对应，`member_ownerships.account_id` 指定该成员所在的健康档案所有者账号的私有库。`MemberRepository` 以认证库为主事务附加健康档案所有者账号的成员库，创建和删除两端记录，并核对该账号的成员归属登记集合与成员资料集合完全一致。任一端缺失或多出记录时按不受支持的 Schema 处理。

`settings.db.member_preferences.default_member_id` 和 `last_member_id` 直接引用 `auth.db.member_ownerships.member_id`。`member_ownerships.account_id` 确定健康档案所有者账号的成员库，`member_grants` 确定操作者的共享访问权，该账号 `members.db.members` 中的同名成员资料行接受跨库一致性校验。成员创建、授权、撤权、选择和删除通过 `MemberRepository` 在认证库事务中附加操作者配置库，写入前验证成员资料与当前权限。权限撤销或成员删除时，同一事务选择替代默认成员并修正失效选择；两个字段按各自契约允许保存 `NULL`。

#### 聊天与收藏的成员引用

`conversations.db.conversations.member_id` 直接引用 `auth.db.member_ownerships.member_id`。`MemberRepository` 从该登记读取健康档案所有者账号 `account_id`，再检查该账号 `members.db.members` 中存在同名成员资料行。创建聊天和分叉在成员生命周期锁内执行这项访问与一致性校验，后续执行重新检查授权。撤权保留成员 ID，并把旧聊天限制为历史查看；成员删除事务附加所有操作者的会话库并把该字段置为 `NULL`。详细规则见[成员与健康档案授权](../领域/成员与健康档案授权.md#成员选择默认成员与会话绑定)。

`favorites.db.favorites.member_id` 直接引用 `auth.db.member_ownerships.member_id`。医疗报告收藏通过 `MemberRepository.resolve` 完成健康档案所有者账号解析、权限检查和成员资料一致性校验；消息收藏从已保存的来源聊天读取成员 ID，并通过成员生命周期锁与成员删除确定先后。撤权保留成员 ID 与收藏快照；成员删除事务附加所有操作者的收藏库并把该字段置为 `NULL`。

#### 医疗报告的成员引用

`reports.db.reports.member_id` 和 `report_sources.member_id` 直接引用 `auth.db.member_ownerships.member_id`。`ReportService.for_member` 通过 `MemberRepository.resolve` 读取该登记中的健康档案所有者账号 `account_id`，检查该账号 `members.db.members` 中的同名成员资料行，再打开该账号的 `reports.db`。每次医疗报告操作都使用成员作用域查询。成员删除事务附加健康档案所有者账号的医疗报告库并删除该成员的医疗报告、来源和明细。医疗报告库内部的组合外键继续保证各表 `member_id` 一致。详细规则见[医疗报告](../领域/医疗报告.md#医疗报告概念模型)。

`reports.db.report_source_file_cleanup_outbox.member_id` 记录创建清理任务时的所属成员。清理任务所在的 `reports.db` 位于健康档案所有者账号目录；任务在删除来源或成员数据的事务中生成。成员登记和资料可以先删除；任务仍以健康档案所有者账号目录、成员 ID 和受控相对路径独立重试，完成后删除清理任务。

#### 健康日记与用药资料的成员引用

`medical_logs.db.medical_logs.member_id` 以及所有者 `medications.db` 中 `medication_plans`、`medication_inventory` 和成员操作 `medication_requests` 的 `member_id` 引用 `auth.db.member_ownerships.member_id`。Service 通过 `MemberRepository` 解析健康档案所有者、检查成员资料与实时授权，再由 Repository 按成员读取和写入。药品目录和原件没有成员字段，归数据库所在账号；批次与计划按成员隔离并引用同账号目录药品。

`MedicalLogRepository` 直接连接健康日记库，在事务内保存日记内容。

成员删除通过 `member_data_store.py` 的显式参与注册表附加已存在的领域库，删除该成员的日记、计划、库存批次与成员写入请求记录，目录药品与药品原件继续保留。医疗报告和身体指标来源按所属领域执行清理。缺失领域库不因删除而创建。

#### 用药写入请求的账号与对象引用

`medication_requests.actor_account_id` 引用 `auth.db.accounts.account_id`，表示发起写入请求的操作者；请求记录保存在健康档案所有者数据库中。Service 在当前授权下确定该账号，Repository 以 `(actor_account_id, request_id)` 去重。

`medication_requests.object_id` 根据 `operation` 分别指向同库的 `medications.medication_id`、`medication_plans.medication_plan_id` 或 `medication_inventory.medication_batch_id`。该关系不设外键，目标允许先删除。`MedicationRepository` 与 `MedicationSourceRepository` 在创建事务中保存对象及去重记录；重试时比较成员、操作类型与内容哈希，相同请求返回已有对象，目标已删除时返回不存在，不同内容复用标识时返回冲突。

#### 公共通知的业务引用

notifications 和 notification_outbox 的 member_id、resource_type/resource_id 引用业务对象，允许对象先删除，不定义跨库外键。通知 Service 通过登记的业务能力批量验证。用药通知在成员授权保护内读取；回答通知的 member_id 为空，resource_type 为 conversation，resource_id 引用接收账号的 conversations.session_id，validity_key 保存完成的 turn_id。账号隔离、轮次成功状态与聊天存在性由 Service 和业务读取能力验证。对象删除、撤权或安排失效时取消并隐藏相应通知，已取消记录不恢复。

回答和完成事件先保存至 JSONL；会话索引库作为文件主库，与发起账号的通知发件箱使用 DELETE 日志、FULL 同步的跨库事务一起提交完成索引和待发送事项。接收账号通知先提交，再按事件和修订标记发件箱完成；重试由稳定通知主键去重。公共检查进度按账号和任务保存固定恢复区间，不引用单个用药计划。详见[站内通知](../领域/站内通知.md)。

#### 会话索引与事件日志

`conversations.db.conversations.session_id` 和 `relative_path` 共同定位同一账号目录中的一份会话 JSONL。header 的 `id` 等于 `session_id`，`accountId` 等于目录账号 ID。`ConversationRepository` 生成固定相对路径，并在创建、读取、分叉和删除时核对路径、header 与调用身份。缺失文件、孤儿文件或身份不一致属于会话存储损坏；数据库行与文件删除属于跨 SQLite 与文件系统操作，由只读实例盘点检查。准确 JSONL 结构见[会话 JSONL 格式](会话JSONL格式.md#与-conversationsdb-的对应关系)。

`conversations.db.conversations.parent_session_id` 和 `seed_event_count` 引用分叉来源聊天及其复制到子 JSONL 的稳定事件前缀。分叉时 Repository 校验完整轮次边界并同时写入子索引和 header。`parent_session_id` 不使用自引用外键，父聊天允许先删除，子聊天继续独立存在并保留血缘标识。

`conversations.db.conversation_turns.turn_id`、`user_message_id`、`final_assistant_message_id` 和 `stream_id` 引用同一 `session_id` 会话 JSONL 中的 `turn/start`、用户消息、助手消息及流式执行标识。JSONL 是完整执行记录的可信源，Repository 在追加事件时更新索引，并能从事件重新核对和重建轮次索引。消息或轮次标识与 JSONL 不一致时按会话存储损坏处理。

#### 会话附件

`conversations.db.conversation_resources.relative_path` 和 `(session_id, resource_id)` 定位账号附件目录中的不可变文件。资源随消息使用后也出现在同一会话 JSONL 的附件元数据和资源引用中。Repository 限定路径位于账号附件目录，校验写入状态、大小与 SHA-256，并在发送或排队时固化资源关系。分叉可以为子聊天创建新资源行并共享原文件；最后一个有效引用消失后才加入清理队列。

#### 收藏来源

当 `favorites.db.favorites.source_type = 'message'` 时，`source_session_id` 引用操作账号 `conversations.db.conversations.session_id`，`source_id` 引用对应 JSONL 中当前可收藏的助手消息。创建收藏时 API 同时验证聊天、当前消息和成员关联，再保存独立内容快照。来源聊天删除、消息被替代或来源不再可用后，收藏继续保留并返回来源不可用状态。

当 `favorites.db.favorites.source_type = 'report'` 时，`member_id` 和 `source_id` 引用健康档案所有者账号的 `reports.db.reports(member_id, report_id)`，`source_session_id` 为空字符串。创建收藏时服务验证实时授权和目标医疗报告，再保存完整医疗报告快照。医疗报告删除或授权失效后，收藏继续保留并按实时检查返回来源状态。

#### 医疗报告原件

`reports.db.report_sources.relative_path` 引用健康档案所有者账号目录 `reports/attachments/{resource_id}.{ext}` 中的医疗报告原件。`ReportRepository` 只生成和解析受控相对路径，并按成员校验文件大小、SHA-256 与来源关系。删除最后一个医疗报告引用时，数据库事务先删除关系并把文件路径加入清理队列。

#### 用药原件与清理任务

`medication_sources.relative_path` 引用健康档案所有者账号目录 `medications/files/` 下的直接子文件，只保存文件名。`MedicationService` 在调用文件 Repository 前检查成员与药品归属，生成受控路径并保存文件 SHA-256；Service 读取时复查权限，Repository 校验路径、文件存在性与哈希。保存后的原件独立于聊天附件生命周期。

`medication_source_cleanup_outbox.relative_path` 记录待清理文件的位置，所属账号由数据库及原件目录确定。删除目录药品时，在删除索引的事务中登记清理任务；上传失败后文件未能删除时也登记任务。成员或原件索引允许先删除，任务不依赖原件外键，按所有者目录与受控路径重试；文件已不存在视为完成。

#### 文件清理任务

`conversation_resource_cleanup_outbox.relative_path` 以及 `report_source_file_cleanup_outbox.member_id`、`relative_path` 定位已经删除或正待删除的资源文件。清理队列不对资源或医疗报告来源建立外键。来源记录允许先删除，物理文件也可能已经不存在；清理器使用受控路径执行可重试删除，文件不存在视为清理完成。

除以上明确允许断开的情况外，代码读取到缺失目标时必须返回明确的数据缺失、权限失效或存储损坏错误。跨存储关系的添加、改名或删除需要同时更新本节、对应 Service 或 Repository、相关领域文档和实例盘点规则。

```sql
CREATE TABLE IF NOT EXISTS account_preferences (
    singleton_id INTEGER NOT NULL,
    notifications_enabled INTEGER NOT NULL DEFAULT 0,
    notifications_enabled_since TEXT,
    medication_due_enabled INTEGER NOT NULL DEFAULT 0,
    medication_due_enabled_since TEXT,
    medication_expired_enabled INTEGER NOT NULL DEFAULT 0,
    medication_expired_enabled_since TEXT,
    answer_completed_enabled INTEGER NOT NULL DEFAULT 0,
    answer_completed_enabled_since TEXT,
    notifications_updated_at TEXT NOT NULL,
    PRIMARY KEY (singleton_id),
    CHECK (singleton_id = 1),
    CHECK (notifications_enabled IN (0, 1)),
    CHECK (notifications_enabled = 0 OR notifications_enabled_since IS NOT NULL),
    CHECK (medication_due_enabled IN (0, 1)),
    CHECK (medication_expired_enabled IN (0, 1)),
    CHECK (answer_completed_enabled IN (0, 1)),
    CHECK (medication_due_enabled = 0 OR medication_due_enabled_since IS NOT NULL),
    CHECK (medication_expired_enabled = 0 OR medication_expired_enabled_since IS NOT NULL),
    CHECK (answer_completed_enabled = 0 OR answer_completed_enabled_since IS NOT NULL),
    CHECK (notifications_enabled = (medication_due_enabled OR medication_expired_enabled OR answer_completed_enabled))
)
```

所有开关默认关闭。总通知开启或关闭时所有子通知跟随；仅设置子通知时，总通知等于三个子通知的逻辑或。联动更新在同一事务中完成，数据库检查规则约束一致性。每个由关闭变为开启的开关记录对应开启时间；重复设置相同值不改变时间。接收起点取总通知与类型开启时间的较晚者，重新开启不补发关闭期间的事件。

业务行数、启用的 Provider、当前联网服务、JSONL 行数和清理任务会随运行变化，不写入当前契约。实例盘点必须注明时间、时区、实际 `DATA_ROOT` 和账号作用域，并使用只读连接；不得输出密码哈希、登录令牌、Cookie、密钥密文、消息正文、Provider payload、工具参数与结果、医疗报告原文或附件内容。

## member_lifecycle.db

由 `storage/member_lifecycle_database.py` 定义，位置为 `all_users/auth/member_lifecycle.db`。保存成员删除与撤权已提交但尚未完成的工作。

### member_lifecycle_tasks

| 字段 | 列定义 | 含义 |
| --- | --- | --- |
| task_id | TEXT NOT NULL | 稳定任务标识 |
| owner_account_id | TEXT NOT NULL | 健康档案所有者账号作用域 |
| member_id | TEXT NOT NULL | 本次变更的成员引用 |
| actor_account_id | TEXT NOT NULL | 受影响会话的操作者账号引用 |
| session_id | TEXT | 受影响会话引用；文件清理任务为空 |
| operation | TEXT NOT NULL | interrupt_session 或 delete_files |
| attempt_count | INTEGER NOT NULL DEFAULT 0 | 已失败次数 |
| next_attempt_at | TEXT NOT NULL | 下次可执行时间 |
| last_error | TEXT | 最近失败信息 |
| created_at | TEXT NOT NULL | 变更登记时间，也限定会话中断范围 |
| updated_at | TEXT NOT NULL | 最近更新时间 |

主键为 `PRIMARY KEY (task_id)`。检查约束为 `operation IN ('interrupt_session', 'delete_files')`、`(operation = 'interrupt_session') = (session_id IS NOT NULL)`、`attempt_count >= 0`。独立索引为 `CREATE INDEX member_lifecycle_ready ON member_lifecycle_tasks(next_attempt_at, task_id)`。

账号和会话位于其它数据库，成员允许先删除，因此不声明外键。`MemberRepository` 在已开始的成员变更事务中附加该库，由 `MemberLifecycleRepository.enqueue` 登记准确目标。认证主库与本次事务的全部附加库必须使用 `DELETE` 日志模式和至少 `FULL` 的同步级别；登记时只检查，不在事务内更新设置。成员更新与任务登记共同提交；任务库创建失败、附加库数量超限、设置不符合要求或登记失败时，成员变更不提交。详细生命周期见[本地存储](本地存储.md)。

`MemberLifecycleTasks` 逐项执行。会话已删除视为完成；中断仅作用于登记时间之前的输入和轮次，避免延迟重试取消重新授权后的新任务。文件清理由医疗报告来源存储再次确认引用。完成即删除任务，失败使用有上限的退避并保留任务。
