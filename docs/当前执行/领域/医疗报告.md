## 字段与解读引用契约

医疗报告公共事实、列表统计和详情分别表达。`flagged_count`、`total_count` 属于列表统计；详情包含 `analysis_updated_at`；`other_report` 使用对象或空值。各类型的字段、存储映射、必填限制和可编辑范围由当前领域 Schema 派生，前端创建与详情编辑共用类型化字段元数据，收藏快照使用相同字段名称。

`write_report_analysis` 在服务端绑定阶段读取当前轮次可信联网 Observation，把解读结果中的合法 `[cite:引用标识]` 转成普通 Markdown 链接后保存。模型不能提交可信引用映射。无法解析时返回 `REPORT_CITATION_UNRESOLVED` 及具体标识，由行动模型决定如何继续；围栏代码、行内代码和转义文本不转换。手工编辑保存普通 Markdown，通用渲染器默认保留未知标记。保存后的解读结果、详情、收藏和复制使用相同链接，不改写既有数据。

## 医疗报告插件与能力边界

医疗报告插件通过通用 `PluginRuntimeContext` 读取可信 `account_id`、固定 `member_id`、模型网关、事件记录器、Observation 解析器、会话资源解析器和隔离的 `ReportService`。成员访问解析同时提供操作者的 `account_id` 与健康档案所有者账号的 `account_id`；`ReportService` 和 `ReportRepository` 始终按健康档案所有者账号 ID 定位医疗报告库，因此账号用户标识更新后仍访问同一成员的医疗数据。

`ConversationService` 不引用医疗报告工具名称，也不根据医疗报告结果选择下一步。插件产生的业务影响通过通用 effect envelope 返回：

```json
{
  "resource_refs": [
    {"resource_type": "report", "resource_id": "LAB-..."}
  ],
  "affected_resource_refs": [],
  "created_entities": [],
  "changed_entities": []
}
```

查询和成功写入使用 `resource_refs` 返回当前可打开的医疗报告快照；删除等操作可用 `affected_resource_refs` 保留已受影响对象的安全展示快照，`created_entities/changed_entities` 只描述当前轮次关系。`ConversationService` 只按通用资源解析器生成消息资源引用和当前 `resource_states`，不解释医疗报告业务。前端根据同一轮次的真实 effect 把医疗报告关系投影为“当前轮次创建/查阅/更新/重新分类/更新解读/关联来源/删除”，并按引用自身的成员与医疗报告身份解析当前资源状态，显示“已更新”“已删除”或“无权访问”；“已删除”和“无权访问”条目禁止点击，不显示医疗报告详情快照；这些展示不更新历史工具结果，也不从回答文本猜测医疗报告。

当前医疗报告 Skill：

| Skill | 能力边界 | 实际授权工具 |
| --- | --- | --- |
| `report-import` | 解析、校验并安全导入当前可见线性会话中的医疗报告；不自动解读 | `create_report`、`link_duplicate_sources`、`merge_report` |
| `report-analysis` | 基于当前轮次真实读取的原始证据生成或重写解读结果 | `write_report_analysis` |
| `report-query` | 只读查询医疗报告、指标和跨医疗报告差异，也是其它医疗报告能力的共享取证入口 | `read_report_catalog`、`read_report_information`、`read_report_analysis`、`read_lab_dictionary` |
| `report-update` | 添加检验指标记录、更新字段或元数据、重分类或删除明确目标 | `update_report_fields`、`add_lab_report_items`、`delete_lab_report_items`、`reclassify_report`、`delete_report` |

Skill 文件可以维护领域操作规程，包括编号步骤、必需取证、条件分支和工具调用顺序。规程由行动模型按需读取并结合真实 Observation 执行；Skill 加载器、Harness、Service 和 Repository 不把它编译或复制为第二套业务状态机，也不通过静态 intent 替模型选择 Skill。导入、解读或更新需要读取当前医疗报告证据时，模型还必须读取 `report-query`；读取某个写入 Skill 不会隐式授权查询工具，也不会由后端替模型加载另一个 Skill。

## 医疗报告工具契约

工具顶层描述遵循项目开发规则，精确参数见[医疗报告工具参数 Schema](../../../backend/app/plugins/medical_report/tools/)。服务端绑定当前成员并检查实时健康档案权限；检验指标分类目录属于该成员的健康档案所有者账号。

工具参数 Schema 只包含模型可决定的业务参数。不可变 `account_id` 由 Runtime 可信绑定，真实文件路径与数据库访问由服务端解析；来源由当前可见用户消息、附件及医疗报告读取 Observation 授权，写入时由服务端校验。

医疗报告目录采用数据库筛选和游标分页，`cursor` 与 `limit` 默认每页 24 条、上限 100 条，返回 `next_cursor` 和完整匹配数量。会话工具只向模型提供日期筛选，Harness 内部保持范围自动读取全部目录页，工具结果以 `pagination` 说明页次和完成状态。医疗报告事实、解读结果及检验指标分类目录按显式选择返回完整内容，内部逻辑页合并为一次工具结果；超过上下文预算时明确失败，不能把部分内容称为完整结果。

## 医疗报告导入

### 最终结构与来源

当前消息文本、图片、PDF 和多个附件由主行动模型整体理解，以确定医疗报告边界和每份医疗报告的全部来源。

允许的可信来源包括：

- `conversation_attachment`：引用当前会话线性视图可见附件 `visible_attachments`（含历史轮已上传且仍可见的附件）中的准确 `resource_id`；附件名统一使用 `original_filename`。
- `conversation_text`：服务端绑定当前用户消息原文，模型不重传文本。
- `report_source`：重分类时引用当前轮次 `read_report_information(fields=["sources"])` Observation 返回的当前医疗报告原件；引用必须包含真实 `read_call_id`、`report_id` 和 `resource_id`。

一个来源可以支持多份医疗报告，多份来源也可以共同支持一份医疗报告。模型不得用文件名、序号、临时别名或猜测值代替真实资源 ID。

### 语料判断

导入判断使用三个独立的只读工具：涉及检验报告时，通过 `read_lab_dictionary` 读取完整检验指标分类目录；通过 `read_report_catalog` 定位相近医疗报告，再通过 `read_report_information` 按需读取医疗报告事实。没有相近医疗报告且证据支持独立创建时，可以直接选择创建新医疗报告，无需读取全部既有医疗报告详情。关联重复来源和无冲突合并必须依据目标医疗报告事实。

查询结果整体超出上下文预算时，模型应缩小筛选或字段后发起新的查询；失败结果不代表已读取部分医疗报告事实。会话历史中的早前导入结果不代表当前医疗报告档案库状态，判重、合并和回答是否已经导入时必须以当前轮次接收的 Observation 为准。

模型根据当前轮次 Observation 选择写入方式：

- 创建医疗报告。
- 为完全重复内容关联来源。
- 对没有旧值冲突的内容执行合并。

查询范围、相近医疗报告选择、判重和下一步动作由模型根据 Observation 决定。后端执行模型提交的查询参数，不自行通过日期、相似度或静态阈值替模型筛选和决定业务处置。

### 事务写入与冲突

三个导入写入工具直接接收 `report` 和 `sources`；`link_duplicate_sources` 和 `merge_report` 还要求 `target_report_id`。工具经由 Service 在写入前校验医疗报告结构、时间、名称、分类、指标和来源，校验通过后完成对应写入。来源文本、附件路径及允许引用的医疗报告原件由当前会话的可信上下文提供，校验失败时返回错误。

Skill 建议及时写入已具备条件的医疗报告，数量较少时也可集中处理。处理节奏由模型自主安排，每次 Observation 继续回到行动循环；结束前核对是否有遗漏。

- 创建时第一个来源成为主来源。
- 关联和合并保持已有主来源。
- 合并只填补缺失字段和新指标。
- 不同旧值或映射歧义返回 `REPORT_IMPORT_WRITE_CONFLICT`。
- 目标医疗报告在写入前已经删除、合并或移走时明确失败，不恢复对象或猜测替代目标。
- 失败调用没有部分写入。

重复判断和写入失败保留在会话 Observation 中，不创建候选、待审、待决、冲突或放弃实体。模型依据工具错误决定后续处理。

### 医疗报告导入与解读隔离

医疗报告在用户没有明确要求“不保存/只查看”时默认导入，但导入不授权医疗报告解读。未获医疗报告解读授权时，Agent 不得顺带总结正常或异常指标、判断医学意义或写回解读结果正文；判重或合并所需的最小差异说明除外。

## 医疗报告查询、解读与修正

### 查询与比较

`read_report_catalog` 用于定位目标，`read_report_information` 用于读取医疗报告事实和原始证据，`read_report_analysis` 只读取既有解读结果。原始证据永不混入 `analysis_content`。

跨医疗报告查询使用 `read_report_information` 读取原始证据，并保留医疗报告日期、`result_text`、`reference_text` 和 `flag_text`。

### 医疗报告解读

用户点击“开始解读”或“重新解读”，或者在当前消息明确要求医疗报告解读，即构成当前写回授权。附件导入本身不构成授权。

`report-analysis` Skill 正文规定原始证据读取要求。`write_report_analysis` 接收 `report_id` 和 `analysis_content`，Runtime 绑定会话与来源消息，Service 在事务中把解读结果写入当前成员的目标医疗报告。

### 会话内修正与删除

明确字段修正（包括就诊时间）、检验报告指标添加与删除、重分类和医疗报告删除分别使用 `update_report_fields`、`add_lab_report_items`、`delete_lab_report_items`、`reclassify_report` 和 `delete_report`。字段更新及指标添加、删除都在单份目标医疗报告内通过同一事务处理一个或多个项目，任一项目无效时不产生部分写入。添加指标必须存在于健康档案所有者账号的检验指标分类目录、主分类与目标医疗报告一致且尚未存在；普通并发更新采用最后有效写入优先，不绑定内容版本。添加或删除指标后既有解读结果标记为过期。删除医疗报告中的检验指标不影响账号检验指标定义；删除后没有剩余指标时明确失败，不自动删除整份医疗报告。

用户已经明确目标和值时无需重复确认；目标、字段、新值或删除对象不明确时自然追问。系统不创建通用变更提案。

重分类还需通过 `read_report_information(fields=["sources"])` 读取目标医疗报告全部已保存原件，主 Agent 基于原始证据形成新结构。`reclassify_report` 接收 `report_id`、`report` 和 `sources`，内部校验后在同一事务中替换结构，保持医疗报告 ID、执行时的医疗报告时间和全部来源不变，全程没有工具内部模型调用。

### 医疗报告页面 CRUD

医疗报告页的手工创建、补充原件、字段编辑、检验指标记录添加与删除、手工解读结果正文编辑和删除是用户已经明确发出的页面命令，直接走 API → Service → Repository，不创建会话、不调用工具、不追加二次业务确认。补充原件只保存并关联用户明确选择的文件，不解析或更新医疗报告事实；目标没有来源时第一份补充的原件成为主来源，已有主来源时保持不变。检验指标添加从目标医疗报告当前分类的账号检验指标分类目录选择尚未存在的指标；删除最后一条指标会失败，不自动删除整份医疗报告。手工创建消费用户已经填写的七类结构化字段，可以没有来源文件；它不同于 Agent 导入使用的 `create_report` 工具，不替用户推断医疗报告边界或医学内容。

页面请求不携带内容版本。目标存在时以后提交的有效操作为准；目标因删除、合并或移动已不存在时，后端返回明确错误，前端保留提示。

## 医疗报告概念模型

医疗报告数据库位于健康档案所有者账号的私有目录。医疗报告业务数据只保存正式医疗报告、可选的正式来源关联、时间戳和解读结果；写入失败只返回会话工具错误。会话导入的医疗报告必须有来源，页面手工创建的医疗报告可以没有来源。

每份正式医疗报告拥有稳定医疗报告 ID，并通过不可变 `member_id` 永久关联一名成员，包含医疗报告类型、名称、医疗报告时间、可选机构以及独立的解读结果正文和过期状态。重分类不改写医疗报告 ID。解析中、冲突中、待确认或异步医疗报告解读等流程状态不进入医疗报告档案库。

医疗报告库中的 `member_id` 对应全局成员归属和健康档案所有者账号的成员资料，但这些记录位于不同数据库，SQLite 不能跨库建立外键。`ReportService` 每次操作都从当前授权解析健康档案所有者账号并限定成员作用域，成员删除事务则把已存在的医疗报告库一同加入同一事务。医疗报告库内部的七类明细表使用 `(report_id, member_id)` 真实外键连接主医疗报告；成员不一致的明细会被 SQLite 拒绝，删除主医疗报告时明细级联删除。

`reports` 的准确列、主外键、默认值、检查约束和索引见[数据库结构中的 `reports.db`](../运维/数据库结构.md#reportsdb)。本文只维护这些值的医疗报告领域语义。

### 来源文件

医疗报告原件保存 MIME 类型、文件字节数、受控相对路径、文件 SHA-256、来源形态和创建时间。文件成为医疗报告来源时，服务端为它生成独立、稳定的医疗报告原件资源 ID，并将原件保存到健康档案所有者账号的 `reports/attachments/{resource_id}.{ext}`。该资源 ID 与会话附件资源 ID 分离；接口中的 `filename` 从受控相对路径提取，不单独存储上传时的原始文件名。医疗报告与原件形成多对多关系，并可标记主来源；一份医疗报告可以关联多个原件，一个原件也可以被多份医疗报告关联。页面手工创建且没有原件的医疗报告不创建虚假来源；用户可以随后通过医疗报告详情补充原件。补充原件按内容拒绝目标医疗报告内的重复关联，整次选择先完成格式、大小和重复校验，再保存并关联，任一文件无效时不产生部分写入。

来源路径只存在于 Repository 控制的数据中，不接受模型或客户端传入。删除医疗报告时，同一事务删除关系并把孤立文件加入文件清理队列；实际文件清理失败可以安全重试，不影响数据库删除结果。仍被其余医疗报告引用的文件不清理。

文件清理队列只保存待处理的成员与相对路径，不连接已经删除的医疗报告或来源记录。这样数据库内容可以先完成删除，文件清理失败时任务仍能独立重试。

会话消息文本作为医疗报告来源时，由服务端保存为受控文本来源；模型不能重传或伪造原文。

### 七类医疗报告事实

- 检验报告保存指标身份、分类、名称快照、结果原文、参考范围原文和结果标记。
- 检查报告保存检查名称、临床诊断、检查方法、检查所见和检查诊断。
- 病理报告保存送检标本、大体检查、病理诊断和取材部位。
- 手术报告保存术前/术中诊断、麻醉、起止时间、输血/失血/尿量/输注/用药、手术经过和术后生命体征。
- 门诊病历保存主诉、现病史、体格检查、辅助检查、诊断、处理意见和补充内容。
- 急诊病历在上述内容之外保存抢救经过、留观情况、出院诊断和出院医嘱。
- 其它医疗报告保存没有适配前六类结构的正式正文。

检验结果标记只允许 `未标记`、`正常`、`异常`、`偏高`、`偏低`；未提供状态时使用 `未标记`。七类医疗报告的准确表、列、PK/FK 和级联规则见[数据库结构](../运维/数据库结构.md#reportsdb)。

### 检验指标分类目录

检验指标分类目录由指标、分类及两者关系组成。指标 ID 稳定，展示名称允许跨主分类重复。每个指标必须有且只有一个主分类，并可关联多个关联分类；检验报告通过稳定指标 ID 引用主分类关系，同时保存当前展示名称。名称或别名只在同一主分类内冲突，不同主分类的同名指标保持不同 ID，编辑和合并均按稳定 ID 定位。目录由健康档案所有者账号内的全部自有成员共用。受邀编辑导入只能补充新指标与别名，不能更新既有分类口径；目录管理只允许操作账号自己的目录。无法唯一匹配的指标不由后端猜测映射。

字典写操作使用 `dictionary_revision` 做 CAS。指标或分类改名、更换主分类会更新受影响医疗报告结构并使既有解读结果过期；分类改名同步更新检验报告名称。增删关联分类保持历史结果不变。指标删除执行级联清理并在响应 `effects` 中返回影响；分类删除条件为主分类关联数为零。

现有指标编辑后的规范名称或别名与同一主分类内另一指标冲突时，API 返回结构化 `LAB_DICTIONARY_NAME_CONFLICT`、冲突目标 `item_id` 和名称，设置页只提供“合并指标”或“放弃编辑”。合并是单事务操作：保留目标规范名称、说明和主分类，把来源规范名称与既有别名并入目标别名，把来源分类并为关联分类，并迁移受影响结果。同一医疗报告，或同一原件与医疗报告时间中已经存在目标指标时，只有结果、参考值和异常标记一致才能去重；任一值不同则返回 `LAB_DICTIONARY_MERGE_RESULT_CONFLICT`，整笔合并不写入。

## 领域验收

- 医疗报告工具目录与当前插件注册保持一致，会话写入始终经工具 → Service → Repository。
- 页面手工创建和传统 CRUD 始终经 API → Service → Repository，不伪装成会话工具。
- 导入依据医疗报告内容和当前轮次按需接收的医疗报告 Observation 作出判断，读取范围和处理节奏由模型自主决定。
- 医疗报告事实和既有解读结果分开读取；医疗报告解读获得明确授权后才写入解读结果。
- 删除、重分类或其它破坏性操作使目标消失后，后续操作明确失败，不恢复对象或猜测替代目标。
- 医疗报告领域概念、来源语义和检验指标分类规则只在本文维护；SQLite 表、列、键、索引与约束见[数据库结构](../运维/数据库结构.md)；物理路径、文件权限和 Schema 生命周期见[本地存储](../运维/本地存储.md)。

## 实现与事务归属

医疗报告插件注册入口组装 Skill、工具与资源适配器。模型提交医疗报告内容和来源引用，工具绑定会话、用户原文、可见附件及已读取原件，`ReportService` 在写入内部校验结构与来源。

`ReportService` 在不可变成员作用域内实时授权，使用独立的医疗报告结构校验、呈现、缩略图和来源存储能力。来源存储完整承担复制、哈希、注册及失败清理，医疗报告查询和医疗报告档案库写入使用相同来源契约。

`LabCatalog` 拥有目录读写，`ReportFacts` 拥有医疗报告使用统计、指标联动、合并冲突检查及事实更新；二者共享显式 `ReportTransaction` 的原 SQLite 连接。目录更新、医疗报告联动、解读结果过期标记、空医疗报告删除和来源文件清理任务在同一事务内提交。目录或事实阶段失败时全部撤销未提交变更；文件删除由已提交清理任务驱动。

## 门诊病历与急诊病历

医疗报告类型固定为检验报告、检查报告、病理报告、手术报告、门诊病历、急诊病历、其它医疗报告。门诊病历使用 `outpatient_report`，急诊病历使用 `emergency_report`；基础信息复用医疗报告结构，`report_time` 表示就诊时间。

两类均保存主诉 `chief_complaint`、现病史 `present_illness`、体格检查 `physical_examination`、辅助检查 `auxiliary_examinations`、诊断 `diagnosis`、处理意见 `treatment_plan`、补充内容 `additional_content`。急诊另保存抢救经过 `rescue_course`、留观情况 `observation_details`、出院诊断 `discharge_diagnosis`、出院医嘱 `discharge_instructions`。全部明细字段为可空文本，原件未记载时留空，保留不确定性和完整原件。

两类完整支持校验、创建、读取、更新、合并、重分类、删除与医疗报告解读；沿用既有事务、来源关联和解读结果机制。事实更新后既有解读结果标记为过期。个人既往史统一维护于[成员既往史](成员既往史.md)，查询某次就诊当时记载的历史情况时读取该次原件。四个医疗报告 Skill 可按任务需要读取既往史；每次 Observation 继续回到动态行动循环。


来源登记、物理写入与文件清理共用医疗报告库写事务检查当前来源身份；有效来源登记会撤销该路径的旧清理任务。手工补充原件在关联事务内按 SHA 校验重复，整批失败不部分关联。检验指标合并去重时将被删除医疗报告的全部来源继承给保留医疗报告；分类迁移允许没有原件的手工医疗报告继承空来源集合。

医疗报告工具直接调用领域服务。导入及重分类写入在 Service 内部复用结构与来源校验算法，来源授权由工具绑定当前会话可信上下文。医疗报告与药品文件清理共享有界轮转批次和逐项失败隔离，持续失败的前部任务不会永久阻止后续任务。
