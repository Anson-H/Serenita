## 从用户目标确定范围

每次选取一个可以独立说明和验收的用户目标，例如“记录并回顾某位成员的身体指标”或“整理一次就医经过”。先明确输入、可见结果、证据、授权和失败处理，再定义具体接口与数据结构。

当前开发命令、配置和路由分别见[后端入口](../../backend/README.md)、[前端入口](../../frontend/README.md)与 [HTTP 接口](../当前执行/接口/HTTP接口.md)。本目录不提供另一套可执行骨架。

## 候选能力与前提

| 候选能力 | 需要解决的工程问题 | 进入版本时的验证重点 |
| --- | --- | --- |
| 身体指标 | 记录来源、测量时间、单位、修正和删除 | 数据可追溯，成员隔离正确，不可比记录得到明确表达 |
| 医疗日志与长期记忆 | 保存授权、来源关联、冲突与过期处理 | 模型推测不成为无依据的事实，用户能查看和纠正 |
| 用药记录 | 药品身份、使用情况、变更来源与时间 | 记录与模型解释可区分，信息不足时有明确反馈 |
| 趋势与就医摘要 | 查询范围、缺失数据、来源定位 | 每项展示有依据，摘要覆盖范围可核对 |
| 提醒与持续任务 | 调度、时区、权限变化、取消和通知 | 不重复产生副作用，取消与撤权及时生效 |
| 设备接入 | 平台授权、同步、重复记录与断连 | 数据来自真实服务，来源与更新时间可核对 |
| 分享与导出 | 资料选择、接收范围、有效期与撤销 | 不越权包含其它成员资料，导出边界清楚 |
| 多智能体协作 | 委派、证据返回、预算和写入协调 | 相比现有行动循环存在可测收益，失败可追溯 |

## 能力接入方式

为领域增加智能体能力时，技能目录描述只说明适用任务和能力范围，技能正文承载判断规则、取证和完成标准。工具顶层描述说明能力与高层返回效果，工具参数结构完整说明准确约束。

每次工具调用返回真实工具结果，形成工具观测并回到动态行动循环。Service 和 Repository 负责权限、事务和存储一致性。页面手工操作使用普通 HTTP API。

不通过新接口预先生成业务步骤，也不在数据接入层根据附件类型替模型决定完整任务流程。

## 数据生命周期

新增记录应有明确的成员归属、来源、修改和删除规则。健康档案授权变化、成员删除及关联文件清理需要在设计时一并定义。

新增数据库保持单一 Python 定义，并同步 Repository、Service、HTTP API、工具参数结构、前端类型与当前文档。跨数据库、会话 JSONL 和文件关系由明确的应用事务及存储规则保证。

本地开发账号、模型与联网配置及配套密钥按项目规则保留。运行时只接受当前契约，不通过启动扫描转换历史数据。

## 进入当前执行

候选能力确定后，将用户目标和产品验收纳入当前产品需求，再把准确规则写入对应领域、架构、接口、前端和运维专题。未来愿景只保留后续增量并链接当前契约。

实现后的验证应覆盖真实能力、证据与授权、数据一致性、失败反馈和用户操作。涉及性能或质量的结论应保留测量依据，不用演示成功代替真实验收。
