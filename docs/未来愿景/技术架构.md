# Serenita 未来愿景：技术架构

> 文档状态：未来愿景 / 不绑定版本
>
> 负责：未来能力的架构约束、技术选项和评估问题。
>
> 当前依据：[技术架构总览](../当前执行/架构/技术架构总览.md)、[智能体运行时](../当前执行/架构/智能体运行时.md)。

## 扩展基础

未来领域能力沿用通用 Agent Harness。系统提示词提供全局边界，Skill 正文提供领域知识和执行要求，工具提供可组合能力；Observation 回到行动循环，由模型决定后续行动。

设备同步等扩展能力沿用现有健康日记和用药记录的 Skill、工具、Service 和 Repository 分工。页面手工操作沿用 API → Service → Repository；会话智能体写入沿用工具 → Service → Repository。

账号身份和成员身份继续使用当前契约。添加资料类型要明确健康档案归属、操作者权限和删除行为，不能因接入新的数据源而另建一套患者身份。

## 数据与证据

未来可探索结构化健康记录、时间序列查询和跨资料搜索。每种能力先定义事实来源、时间、可比性、冲突处理和可追溯方式，再决定存储与索引。

统计、排序、去重校验和数值计算可由确定性工具提供；医学解释由模型在证据与安全边界内完成。聚合结果需要说明覆盖范围、缺失情况和计算方式，并允许按需读取支持当前判断的原始证据。

搜索索引和摘要可以提高定位效率。摘要不是原始证据，搜索命中也不能替代需要实际读取的来源原文。

## 长期资料与记忆

长期记忆采用 SAG 双路召回：Event Description 语义向量召回与 Entity 名称及别名检索共同提供入口，合并结果后沿 Entity 连接和已有 Event 关系扩展，联合选择证据并读取来源原文。Entity 检索的具体算法及融合、排序策略在进入当前执行时确定。Event Graph、Episode 与 Scene 组织健康经历，并支持形成有依据的状态、认识和问题。记忆能力由现有 Harness 按任务调用，Observation 返回行动循环。

独立记忆存储采用 SQLite 保存 Event 等记忆 Record、关系、状态与持久 Projection，采用 LanceDB 作为向量数据库，保存向量及其对应 Record 的引用并提供向量检索。两者均遵循 Append-only，全部记录及派生内容在提交后永久固定并完整保留；新资料与新判断通过追加表达，当前与历史结果按时间和权限读取。对象、状态、追加机制、查询及验证要求统一见[长期记忆与认知架构](长期记忆与认知架构.md)。

扩展领域存储沿用当前成员生命周期与授权机制。准确的数据库定义、字段名和事务边界在能力进入当前执行时统一确定。

## 主动推荐与持续任务

主动推荐通过通用 Agent Harness 使用长期记忆、资料查询和领域能力。用户授权持续关注的成员、问题范围和资料后，新资料到达或定期检查可以唤醒任务；模型根据任务、Skill 和 Observation 判断哪些变化值得关注，是否继续取证、形成建议或结束检查。主动推荐可以发现用户尚未逐项提出的问题，其依据与适用范围需要可追溯。

通用调度能力负责事件触发、定时唤醒、暂停、取消、重试边界和执行记录。它只交付触发事实与授权范围，业务行动仍进入动态行动循环。触发条件不预先指定推荐结论、领域处理阶段或工具调用顺序。每次运行重新校验账号、成员、资料权限和任务有效性；授权变化后不能继续使用先前权限。

主动任务可以结合向量召回、Entity 关联扩展、联合选择和来源原文读取发现跨资料联系，也可以按问题查询精确字段或完整统计。推荐结果保留依据、时间口径、未知部分和形成原因；用户反馈、实际行动与后续结果分别形成有依据的记录，供模型重新判断。

对已经可能产生副作用但结果未知的操作，需要核对真实状态再决定处理方式。应用根据执行结果、接收设置和通知授权，确定性生成、调度与投递通知，并执行频率、免打扰、去重及取消规则。通知类型和调度在应用层装配，设置与已读操作使用普通 HTTP API → Service → Repository；模型通过任务结果提供建议内容，不调用通知工具。

## 多智能体协作

多智能体协作是待验证选项。只有在任务质量、耗时或资源利用有明确收益时，才值得引入。

如开展探索，应由主智能体根据任务动态决定是否委派，子智能体返回证据、不确定性和真实执行结果，供主智能体继续判断。权限、资源预算、取消、并发写入和最终回答责任需要统一约束。

领域专业知识优先通过 Skill 表达。不能按页面、关键词或附件类型固定分发给若干专家，也不能以多数意见替代证据核对。独立子会话并不等于已经具备多智能体协作。

## 资源预算与可靠性

上下文预算根据当前模型能力、输入内容和输出预留计算。大规模记录可以分页、搜索或聚合；具体方式应保留任务所需证据，超出处理能力时返回真实限制。

写入幂等性由操作标识、事务和业务约束保证，不能依赖模型重复生成相同文本。降低采样随机性不能作为数据库幂等保障。

失败应保留真实错误。演示样例只用于明确隔离的展示或测试，不能在真实任务失败时充当成功结果。

## 基础设施选项

当前存储与运行方式以[本地存储](../当前执行/运维/本地存储.md)和开发入口为准。未来长期记忆已确定采用 SQLite 保存 Event 等记忆记录，采用 LanceDB 作为向量数据库；具体 Schema、索引组织、全文检索方案、权限过滤与跨数据库追加一致性在进入当前执行时明确并验证。其它基础设施选型按需要评估：

| 选项 | 值得评估的条件 | 需要回答的问题 |
| --- | --- | --- |
| 服务型关系数据库 | 当前部署或并发需求已超出现有存储适用范围 | 事务、权限、运维和成本是否有实际收益 |
| 时间序列存储 | 连续设备数据的规模和查询已形成明确需求 | 保留周期、降采样及原始数据追溯如何处理 |
| 图关系存储 | 有具体的关系查询需求且现有方案不足 | 关系依据、更新和错误修正如何维护 |
| 容器与独立任务服务 | 部署隔离或持续任务需要独立生命周期 | 增加的运维复杂度是否合理 |

选择新技术时直接形成新的唯一执行契约；不为尚未发布的旧方案增加兼容层或自动迁移流程。

## 评估方式

未来实验应记录任务样本、模型与配置、输入规模、运行环境、测量时间和失败情况。分别观察完成质量、证据准确性、授权遵循、耗时、费用及中断恢复。

性能目标需要结合真实场景制定。未经测量的延迟、可用性和压缩率只可作为待验证假设，不能写成已达标结果。
