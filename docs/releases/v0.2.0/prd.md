## 2. 版本定位

v0.2.0 是 v0.1.0 之后的报告场景规划版本。当前仓库开发不直接执行本文件；进入开发前需要重新核对当前执行版本的范围、接口、认证和存储约定。该版本在 v0.1.0 的登录、模型配置、首页基础对话、会话历史、文件上下文和收藏闭环稳定后，规划新增报告上传、解析、分析、查看、趋势追踪和报告自然语言对话能力。

v0.2.0 的核心目标是：

- 报告智能体（`ReportAgent`）作为报告领域的统一智能编排入口，负责识别任务、选择 Skill、按需调用 Tool 并生成结果。
- 用户可批量上传检验、检查、病理、手术或其它健康报告文件。
- 系统可将报告解析为结构化数据并写入患者私有目录。
- 系统在报告入库后询问用户是否继续分析。
- 用户可在报告场景中查看报告列表、报告详情、分析结果和指标趋势。
- 用户可通过自然语言查询最近报告、异常指标、跨报告趋势和多份报告对比；报告聊天在报告场景左侧承接，右侧保持可折叠报告面板。
- 用户可通过自然语言修正结构化报告数据；写入前必须确认，确认后直接更新报告数据库。
- 系统可识别同一医学报告的重复上传，将电子截图、扫描纸质版等不同原始来源关联到同一份结构化报告记录，避免重复污染列表、趋势和分析。
- 报告数据、分析结果和收藏快照均绑定当前 `account`。

### 2.1 报告智能体核心架构与当前有效口径

本节是 v0.2.0 报告场景的阅读导航。后文保留完整需求、流程、页面状态和验收细节；若局部描述存在理解空间，以本节的报告智能体定位、模块边界和有效口径为准。

#### 2.1.1 报告智能体（ReportAgent）核心定位

v0.2.0 采用单一报告智能体（`ReportAgent`）作为报告领域的智能编排核心。用户上传、报告对话和后台分析任务进入报告领域后，由 `ReportAgent` 识别任务、加载匹配的 Skill、基于上下文完成模型推理，并在需要外部证据或受控动作时发起工具调用。

```text
用户上传 / 报告对话 / 后台分析任务
  -> ReportAgent 识别任务并加载 Skill
  -> 模型基于当前上下文生成候选、分析、解释或结构化草稿
  -> 需要外部证据或动作时调用 Tool
  -> ReportService / Action Layer 校验并执行确定性业务规则
  -> ReportAgent 基于执行结果生成最终内容
```

视觉解析模型负责从上传文件中生成报告大类和结构化字段候选；`ReportSegmentationService` 校验报告边界、分类和拆分规则；`ReportService` 负责判重、入库、权限和事务。所有持久化结果以后端校验为准。

#### 2.1.2 报告智能体（ReportAgent）、Skill、Tool 与后端服务边界

| 层级 | 负责 | 典型能力 | 执行边界 |
| --- | --- | --- | --- |
| 大模型 / 报告智能体（`ReportAgent`） | 理解用户意图、基于已有上下文推理、生成解释、分析和结构化草稿 | 问答、总结、异常说明、分析板块组织、修正建议 | 生成内容属于模型自身能力；需要外部数据或动作时才发起工具调用 |
| Skill | 封装可复用的报告工作流程、判断步骤、参考资料和输出规范 | 报告导入、报告分析、报告查询、报告修正流程 | Skill 可编排工具；权限、事务和确定性业务规则由后端服务执行 |
| Tool | 访问模型上下文之外的数据或执行受控动作 | 读取报告证据、调用外部文件解析服务、创建待确认动作 | 工具必须使用明确 schema、绑定当前 `account` 并接受后端校验 |
| ReportService / Action Layer | 执行确定性业务规则和真实状态变更 | 分割、分类校验、判重、入库、分析失效判断、确认写入、删除 | 所有持久化和状态变更以后端校验结果为准 |

第一版可复用以下报告 Skills：

| Skill | 适用功能 | 工作流边界 |
| --- | --- | --- |
| `report-ingestion` | 上传后的解析、分割、重复候选处理和结构化入库 | 组织导入步骤；报告分割、分类校验、判重和写入规则由后端服务强制执行 |
| `report-analysis` | 用户首次分析和同日证据变化后的自动重跑 | 组织证据选择和分析输出；触发、失效标记、结果校验和写回由 `ReportAnalysisService` 执行 |
| `report-query` | 自然语言列表、详情、指标、趋势、对比和报告追问 | 识别查询目标、读取必要证据并由模型直接生成回答 |
| `report-correction` | 指标修正、元数据修改和删除请求 | 定位目标、形成结构化变更草稿并创建待确认动作；确认后的真实写入由后端 action 执行 |

简单的列表、详情、状态查询继续使用业务接口。同日分析失效判断和后台任务触发由后端事件流程执行。详细的 Skills、业务 intents、工具契约和确认机制见技术文档第 10 章。

#### 2.1.3 当前有效口径

| 主题 | 当前口径 |
| --- | --- |
| 批量上传 | 单批可选择多个图片或 PDF；每个文件形成独立源文件记录并单独解析、判重和入库 |
| 原始文件 | 每个上传文件形成一个源文件记录；源文件可被拆分并关联到多份报告 |
| 解析模型 | 报告图片与 PDF 固定使用当前账号的 `vision_parse` 默认模型生成分类和结构化候选 |
| 报告分割 | 检验报告按功能分类拆分，其它类型按独立报告单或文档边界拆分，再判重和入库 |
| 检验报告 | 肝功能、肾功能、血脂等不同功能分类必须拆成不同 `LAB-` 报告；同一功能分类下的多个指标保存在同一报告 |
| 检验结果存储 | 指标结果和参考值按报告上的完整原始文本保存；解析时判断异常或偏高记为 `↑`，偏低记为 `↓`，无异常或无法判断时不保存标记 |
| 检查报告 | 按独立检查报告单边界拆为 `EXAM-` 报告，结构化提取检查名称、检查时间、临床诊断、检查方法、检查表现、检查诊断或结论 |
| 病理报告 | 按独立病理报告单边界保存为 `PATH-` 报告；结构化分类固定为送检标本、巨检、诊断、取材位置 |
| 手术报告 | 按独立手术记录边界保存为 `SURG-` 报告；联合术式保存在同一报告中 |
| 其它报告 | 按独立文档边界拆为 `OTHER-` 报告，保存报告名称、时间和完整原文 |
| 指标字典 | 新报告出现未收录的检验指标时自动新增为 `pending` 指标，并立即参与展示、查询和趋势 |
| 趋势范围 | 历史趋势只覆盖检验报告；检查、病理、手术和其它报告可在对话中比较原文 |
| 报告聊天 | 复用现有会话表与消息接口，只有实际读取或操作报告的消息保存报告引用 |
| 聊天布局 | 打开报告后可进入左侧聊天、右侧报告的分栏模式；右侧报告可折叠，聊天末尾、输入框上方显示报告和文件索引 |
| 参考值 | 只保存并展示报告自身的参考值原文，不解析上下限或建立复杂参考范围规则 |
| 重复报告 | 同一拆分后报告的不同来源文件默认关联到已有报告 |
| 分析触发 | 用户点击“开始分析”后生成该报告自己的首次分析 |
| 分析刷新 | 已分析报告被同日后续报告补充或验证时，后端后台自动重跑受影响分析 |
| 原始文件修正 | 用户确认后直接修改报告数据库中的指标原文字段，原始文件保持不变 |

#### 2.1.4 模块边界

| 模块 | 负责 | 不负责 |
| --- | --- | --- |
| 上传与源文件管理 | 文件校验、源文件保存、文件哈希、上传来源记录 | 报告医学语义分析 |
| 报告分割 | 将一个源文件拆为 `LAB-`、`EXAM-`、`PATH-`、`SURG-`、`OTHER-` 报告候选 | 重复报告确认、趋势计算 |
| 重复报告识别 | 对拆分后的报告候选做业务指纹判重，生成待确认动作 | 静默覆盖已有结构化数据 |
| 结构化入库 | 写 `reports` 和对应子表，关联原始文件 | 自动生成首次分析 |
| 智能分析 | 基于当前报告和当次临时读取的数据生成 `analysis_sections` | 修改原始报告文件 |
| 后台分析刷新 | 新证据影响既有分析时自动重跑受影响报告 | 新增首页分析更新卡片 |
| 报告查看与趋势 | 展示列表、详情、分析结果、趋势和状态 | 前端自行跨报告聚合趋势 |
| 自然语言查询与修正 | 查询、对比、问答、生成待确认修正动作 | 未确认直接写库 |
| 收藏扩展 | 保存分析或问答快照 | 删除或修改源报告 |

#### 2.1.5 主链路概览

```text
上传源文件
  -> 保存源文件和哈希
  -> 多模态解析
  -> 按报告边界拆分
  -> 对每个拆分后报告做重复识别
  -> 用户处理重复候选或正常入库
  -> 写结构化报告和源文件关联
  -> 展示入库确认卡片
  -> 用户选择是否首次分析
  -> 若后续同日证据影响既有分析，后端后台自动重跑受影响分析
```

#### 2.1.6 关键状态分组

| 状态组 | 关注对象 | 关键状态 |
| --- | --- | --- |
| 上传解析 | 源文件 / 拆分候选 | 上传中、解析中、疑似重复、解析失败、入库完成 |
| 报告存储 | 拆分后的报告记录 | `uploaded`、`parsing`、`parsed`、`parse_failed` |
| 报告分析 | 单份报告分析 | 未分析、分析中、已分析、分析失败、分析可能过期 |
| 后台刷新 | 已分析报告 | 等待后台重跑、后台重跑中、已刷新、重跑失败 |
| 写入确认 | 修正、删除、重复处理 | 待确认、已确认、已取消、已过期、冲突 |

## 3. 版本范围

### 3.1 继承 v0.1.0 的能力

v0.2.0 默认继承 v0.1.0 已定义的以下能力；进入开发前必须与当前执行版本重新核对：

- 基础登录、登录态保持和退出登录
- 账号设置页 `/setting`，包括用户名称修改、密码修改和模型服务管理
- 模型服务、API key、API 地址、连接测试、已添加模型和默认模型配置
- 首页基础对话
- 文件上下文资源、思考模式、会话持久化、流式输出和生成中取消；真实异步模型生成接入后继续验收轮次状态恢复
- AI 回答收藏
- `我的收藏` 列表和取消收藏
- 会话、收藏与 `account` 的数据隔离

上述能力在 v0.2.0 中不作为新增重点，除非报告场景需要扩展其数据来源或入口。

### 3.2 v0.2.0 新增能力

v0.2.0 只新增报告场景：

- 报告上传入口
- 报告批量上传与逐文件处理状态
- 报告多模态解析
- 重复报告识别、确认和多来源文件关联
- 报告结构化入库
- 报告分析确认机制
- 报告智能分析
- 报告列表、筛选和排序
- 单份报告详情
- 报告修改与删除
- 指标历史对比和趋势图
- 报告自然语言查询、对比和上下文问答
- 报告指标原文字段自然语言修正
- 报告分析内容收藏
- 报告场景快捷问题

### 3.3 非本期范围

以下内容不纳入 v0.2.0：

- 生活场景
- HealthKit 或其它设备数据接入
- 医生端、后台管理端、人工审核后台
- 完整患者档案
- 报告导出和分享
- 找回密码、多角色权限管理
- 多智能体会诊、完整医学参考范围知识库、医生端人工审核后台
- 不同实验室或试剂体系之间缺少明确规则的复杂单位自动换算

## 4. 目标用户与核心场景

### 4.1 目标用户

- 慢病患者：如糖尿病、高血压、高脂血症等需要长期复查的人群
- 周期性复查用户：需要持续对比指标变化的人群
- 患者家属：帮助家人理解报告和后续建议的人
- 产品演示和测试用户：用于验证报告链路是否可闭环

### 4.2 核心场景

| 场景 | 用户诉求 | 期望结果 |
| --- | --- | --- |
| 拿到新报告 | 上传后快速知道有没有异常 | 报告入库、异常指标标注、是否分析确认 |
| 报告解读 | 想知道最重要的问题是什么 | 结构化分析板块和下一步关注重点 |
| 复查对比 | 想知道比上次好还是差 | 历史变化方向和趋势图 |
| 深入追问 | 想理解某个指标含义 | 基于当前报告上下文的问答 |
| 长期回顾 | 想查历史报告 | 报告列表、筛选、详情和已存分析 |

## 5. 信息架构

### 5.1 页面结构

v0.2.0 沿用患者主工作台框架，在 v0.1.0 基础上正式交付报告场景。

本期涉及以下已有页面和新增场景：

- 登录页：沿用 v0.1.0。
- 首页：沿用 v0.1.0 的对话承接区，并新增报告上传后的进度、确认卡片和分析结果承接。
- 报告场景入口：本期正式交付，用于查看报告列表、报告详情、检验指标趋势和报告聊天。
- 生活场景入口：视觉占位，本期不交付生活管理能力。
- 我的收藏：沿用 v0.1.0，并扩展支持报告类收藏。
- 账号设置：沿用 v0.1.0 的正式账号设置页 `/setting`。
- 原始文件：左侧辅助入口占位。

### 5.2 左侧导航区

左侧区域从上到下包含：

- 品牌区：展示 `Serenita`
- 场景入口：`报告`、`生活`
- 按钮：`开启新对话`
- 对话记录区：展示最近会话
- 底部辅助入口：`原始文件`、`我的收藏`
- 当前登录用户摘要：展示当前 `user_name` 或 `account`；点击后直接进入 `/setting`

左侧导航栏在所有场景下保持固定，不因场景切换而改变布局或控件组成。

v0.2.0 中，`我的收藏` 需支持报告类收藏；`账号设置` 沿用 v0.1.0 的 `/setting` 页面能力；`原始文件` 可为占位状态。

### 5.3 右侧主工作区

右侧区域从上到下包含：

- 场景内容区：根据当前场景渲染不同内容。
  - `首页`：展示问候标题、健康卡片、对话线程、AI 结果卡片和重要记录。
  - `报告`：默认展示报告列表和报告详情；点击“聊天”后切换为左侧聊天、右侧报告的分栏模式，右侧报告面板可折叠。
  - `生活`：可仅保留标题、占位内容或轻量引导。
- 底部共享输入区：不随场景切换重建或更换结构。

底部共享输入区在视觉和交互上包含：

- 快捷问题按钮组：根据当前场景展示对应 `suggestions`，点击后填充输入框。
- 输入容器：包含隐藏文件选择控件、已上传附件提示、多行文本输入框。
- 操作区：左侧为 `+` 文件上传按钮；右侧为思考模式选择器和主操作按钮。
- 思考模式：至少支持 `默认`、`快速`、`低`、`中`、`高`，选择结果写入 `thinking_mode`。
- 主操作按钮：有文本时显示发送箭头并触发提交；无文本时显示语音图标，但真实语音能力不属于 v0.2.0 交付范围。

交互行为要求：

- `首页`、`报告`、`生活` 统一维护输入文本、附件、错误信息和思考模式选择。
- 从 `生活` 场景发起普通文本提交时，界面切回 `首页` 展示大模型处理结果。
- 在报告聊天模式提交文本时，界面保留在报告场景，回答展示在左侧聊天区域。
- 在 `报告` 场景点击“分析此报告”时，界面同样切回 `首页` 展示分析进度和结果；报告列表的选中状态应保留。
- 文件上传由共享输入区的回形针按钮触发；v0.2.0 中该入口正式支持报告文件上传，并应在上传后刷新报告列表。

v0.2.0 中，`报告` 场景为正式交付能力；`生活` 场景为视觉占位，不纳入本期功能验收。思考模式入口需在视觉上存在，至少支持 `默认`、`快速`、`低`、`中`、`高` 五档选择。

### 5.4 底部统一输入区设计

底部统一输入区位于右侧主工作区的场景内容之后，在 `首页`、`报告`、`生活` 三个场景中保持同一套结构。

输入区从上到下包含：

- 快捷问题区：展示当前场景对应的快捷问题按钮，点击后将问题填入输入框。
- 输入主体区：多行文本输入框，展示当前场景的场景化占位文案。
- 操作区：左侧为文件上传按钮，右侧为思考模式选择器和发送按钮。

控件要求：

- 文件上传按钮使用回形针图标。
- 思考模式选择器展示当前模式，点击后展开 `默认`、`快速`、`低`、`中`、`高` 五档。
- 有文本时，右侧主按钮为发送按钮；无文本时，可显示为语音入口样式，但 v0.2.0 不要求真实语音能力。
- 模型思考与输出过程中均应阻止重复提交，并展示明确加载状态。
- 切换场景时，输入区控件位置不变；不同场景可保留各自的输入内容、附件和错误状态。
- 报告场景的普通浏览模式沿用共享输入区；进入报告聊天模式后，输入区归入左侧聊天区域，右侧报告面板保持可见并允许折叠。

### 5.5 首页定位

首页仍是实时 AI 交互结果的承接场景。

报告上传和报告分析可从首页或报告场景发起，首页负责展示：

- 上传中
- 解析中
- 入库完成确认卡片
- 分析中
- 分析结果
- 从首页直接发起且未绑定报告面板的报告查询回答

### 5.6 报告场景定位

报告场景同时承担报告查看和报告上下文对话。

报告场景用于：

- 查看已上传报告列表
- 筛选和排序报告
- 查看单份报告结构化详情
- 查看已存储分析结果
- 查看检验指标趋势
- 触发“分析此报告”
- 围绕当前报告或多份历史报告发起自然语言查询、对比和追问
- 发起结构化数据修正，并在用户确认后写入
- 在左侧聊天、右侧报告的分栏模式中持续对话
- 折叠或展开右侧报告面板
- 在聊天末尾查看当前会话实际读取或操作过的报告和原始文件索引

## 6. 用户流程

### 6.1 报告上传与入库流程

1. 用户登录后进入首页或报告场景。
2. 用户通过底部输入区点击文件上传入口。
3. 用户一次选择一个或多个 PDF、JPG、PNG 或 HEIC 报告文件。
4. 系统逐文件校验格式和大小，并校验登录态与整批数量限制。
5. 前端切回首页并展示“上传中”状态。
6. 每个文件上传完成后独立进入“解析中”状态；单个文件失败不阻断同批其它文件。
7. 后端使用当前账号的 `vision_parse` 默认模型解析报告内容。
8. 系统先按报告边界拆分源文件；检验报告按功能分类拆分，检查、病理和手术报告按独立报告单边界拆分，其它报告按独立文档边界拆分。
9. 系统根据文件哈希和拆分后报告的业务指纹检查是否疑似同一医学报告。
10. 若未发现重复候选，系统按报告类型写入结构化数据。
11. 若发现重复候选，进入重复报告确认流程。
12. 用户可选择将本次文件作为已有报告的补充来源、用本次解析结果更新已有结构化数据，或仍作为新报告保存。
13. 入库或重复处理完成后，系统按文件和拆分后的报告展示处理结果与确认卡片。
14. 确认卡片展示报告类型、报告名称或功能分类、报告时间、指标数量、异常数量和操作按钮。
15. 用户可选择“开始分析”或“暂不分析”。

### 6.2 报告分析流程

1. 用户在入库确认卡片点击“开始分析”，或在报告详情页点击“分析此报告”。
2. 系统进入“分析中”状态。
3. 后端基于当前报告结构化数据和患者历史报告生成分析。
4. 分析结果按板块展示在首页。
5. 系统将分析结果写回报告数据库。
6. 分析结果底部提供“查看该报告”按钮。
7. 用户点击后进入报告场景，并自动打开对应报告详情。

### 6.3 报告查看流程

1. 用户进入 `报告` 场景。
2. 系统加载当前 `account` 下的报告列表。
3. 用户可按报告类型、时间范围和排序方向筛选。
4. 用户点击某份报告。
5. 系统展示报告基本信息、结构化数据和分析结果；检验报告同时展示指标趋势图。
6. 若报告尚未分析，展示“分析此报告”入口。
7. 检验报告允许切换指标查看趋势。

### 6.4 报告自然语言查询与问答流程

1. 用户打开一份报告并点击“聊天”，主工作区切换为左侧聊天、右侧报告的分栏模式。
2. 系统识别问题属于报告列表查询、报告详情查询、指标查询、趋势查询、报告对比或单份报告追问。
3. 当前报告作为本轮消息的报告上下文资源；若问题涉及“最近一次”“今年”“最近三次”等范围，系统按当前 `account` 检索并把实际引用的报告加入消息上下文。
4. 左侧聊天区域展示基于结构化报告数据、已存分析结果和必要原文生成的回答，右侧报告保持打开。
5. 用户可折叠右侧报告面板，为聊天区域释放空间。
6. 聊天末尾、输入框上方的文件索引展示对话中实际读取、修改、确认写入或分析的报告及其原始文件；点击索引可在右侧打开对应内容。
7. 会话沿用现有会话历史保存，并出现在全局左侧导航栏；打开历史会话时根据消息中的报告引用恢复右侧报告。
8. 若回答有价值，用户可收藏。

上述问题类型是产品能力边界。实现层可复用受控的数据读取、证据检索和回答生成能力来完成列表、详情、异常项、趋势与对比。

示例问题：

- “ALT 最近半年趋势怎么样？”
- “今年有哪些异常指标？”
- “这次肝功能比上次好了吗？”
- “乙肝相关指标有没有阳性？”
- “5 月和 11 月两份报告差异在哪？”

### 6.5 报告自然语言修正流程

1. 用户通过自然语言指出结构化数据错误，例如“ALT 不是 65，是 56”。
2. 系统定位当前 `account`、目标报告、目标指标和待修改字段。
3. 若报告或指标不明确，系统先追问澄清，并以明确目标作为写入前提。
4. 系统生成待确认变更，展示原值、新值、影响字段和来源说明。
5. 目标报告及其原始文件出现在聊天末尾、输入框上方的文件索引中。
6. 用户确认后，系统更新结构化报告数据。
7. 已有分析结果应标记为可能过期，并提示用户是否重新分析。

原始 PDF、图片或其它上传文件不因结构化数据修正而被修改。
待确认内容和确认结果保留在原有对话消息与 `pending_action` 中，`reports.db` 不建立独立修订记录。
自然语言修正生成待确认变更；数据库写入必须经过确认流程。

### 6.6 报告收藏流程

1. 用户在报告分析结果或报告问答回答上点击收藏。
2. 系统生成收藏快照。
3. 收藏记录绑定 `account`、`source_type`、`source_id` 和内容快照。
4. 用户进入 `我的收藏` 后可查看该收藏。
5. 若原报告仍存在，收藏详情可提供“查看原报告”入口。
6. 取消收藏删除收藏记录。

## 7. 功能需求

### FR-001 报告上传入口

- 首页和报告场景的底部输入区均应提供文件上传入口。
- 上传入口支持 PDF、JPG、PNG、HEIC。
- 单批支持选择多个文件，第一版单批最多 20 个文件。
- 单文件大小上限为 20MB。
- 每个文件独立显示上传、解析、重复待确认、成功或失败状态；部分文件失败时继续处理同批其它文件。
- 上传前必须存在有效登录态。
- 上传请求必须绑定当前 `account`。
- 文件格式或大小不符合要求时，应在前端给出明确提示。
- 上传开始后，界面应切回首页展示处理进度。

### FR-002 报告多模态解析

- 上传完成后，系统自动进入解析流程。
- 报告图片和 PDF 固定使用当前账号的 `vision_parse` 默认模型解析；未配置可处理对应 MIME 的视觉解析模型时，应提示用户先完成配置。
- 解析目标是从报告原文中提取结构化信息。
- 检验报告至少提取：
  - 指标名称
  - 结果原文，包括报告中的数值、单位或定性结果
  - 参考值原文
  - 根据结果原文和报告自身参考值判断的异常方向
  - 报告时间或采样时间
  - 功能分类
- 检查报告至少提取：
  - 检查名称
  - 检查时间
  - 临床诊断
  - 检查方法
  - 检查表现
  - 检查诊断或结论
- 病理报告的结构化分类固定为：
  - 送检标本
  - 巨检
  - 诊断
  - 取材位置
- 手术报告的结构化分类固定为：
  - 术前诊断
  - 术中诊断
  - 麻醉方法
  - 开始时间
  - 结束时间
  - 是否输血
  - 术中失血量
  - 术中尿量
  - 术中输血量
  - 术中输液量
  - 术中其他用药
  - 手术经过
  - 术后生命体征
- 其它报告提取报告名称、报告时间和完整报告原文。
- 解析中应展示加载状态。
- 解析失败时应展示失败原因和重试入口。
- 解析失败不应删除已上传原始文件。

### FR-003 结构化入库

- 报告原始文件应保存到当前患者私有目录。
- 报告结构化数据应写入当前患者报告数据库。
- 一个源文件可拆分为多条报告记录。
- 同一拆分后的报告记录可关联多个原始文件来源，例如电子截图、纸质扫描件和 PDF；默认只保留一份 canonical 结构化报告记录。
- 检验报告必须按功能分类拆分为独立 `LAB-` 报告。若同一张检验报告单包含肝功能、肾功能和血脂，应生成三份 `LAB-` 报告。
- 每份 `LAB-` 报告对应一个主要功能分类；同一功能分类下的多个指标保存在同一份 `LAB-` 报告中。
- `report_id` 前缀用于区分报告类型：
  - `LAB-`：检验报告
  - `EXAM-`：检查报告
  - `PATH-`：病理报告
  - `SURG-`：手术报告
  - `OTHER-`：其它报告
- `reports` 表保存报告元数据。
- 检验指标写入 `lab_test_report`。
- 检查报告写入 `examination_report`。
- 病理报告写入 `pathology_report`。
- 手术报告写入 `surgery_report`。
- 其它报告写入 `other_report`。
- 入库完成后，`storage_status` 更新为 `parsed`。
- 入库成功后，报告必须出现在报告列表中。
- 疑似重复报告经用户确认后才可作为新报告写入列表和趋势。

### FR-004 指标字典匹配

- 检验指标入库前应匹配公共指标字典。
- 优先按 `item_id` 或 `item_cn` 精确匹配。
- 精确匹配失败时，使用 `aliases` 进行别名匹配。
- 仍无法匹配时，系统必须自动新增指标。
- 动态新增指标的 `status` 设为 `pending`。
- `pending` 指标可正常展示、入库、分析和参与趋势计算。
- 新指标首次出现即可完成收录，不依赖预设的首批指标范围或人工审核后台。
- 新指标的名称、别名和所属功能分类由解析候选与应用层校验后写入公共指标字典。

### FR-005 入库后确认分析

- 报告入库完成后进入待确认分析状态。
- 首页必须展示入库确认卡片。
- 确认卡片至少包含：
  - 报告类型
  - 报告名称或功能分类
  - 报告时间
  - 指标数量或条目数量
  - 解析后得到 `↑` 或 `↓` 的指标数量
  - “开始分析”按钮
  - “暂不分析”按钮
- 用户点击“暂不分析”后，报告保留 `parsed` 状态。
- 用户点击“开始分析”后，才进入分析流程。

### FR-006 智能分析

- 分析应基于当前报告结构化数据。
- 若存在同类历史报告，应纳入历史对比。
- `report-analysis` Skill 应统一首次分析和后台自动重跑的证据选择、输出结构与医学表达约束。
- 报告智能体（`ReportAgent`）基于证据直接生成分析内容；生成解释、总结和结构化分析板块属于模型自身能力。
- `ReportAnalysisService` 负责触发条件、证据范围校验、输出 schema 校验、状态更新和结果写回。
- 分析结果应结构化展示。
- 分析结果按以下板块组织，无内容的板块不展示：

| 板块 | 含义 |
| --- | --- |
| 好消息 | 恢复正常或明显改善的指标 |
| 稳定信号 | 持续在正常范围内的指标 |
| 僵持点 | 长期异常但未恶化的指标 |
| 微小波动 | 轻微变化，暂不需要干预 |
| 需注意信号 | 新出现异常或恶化趋势的指标 |
| 近期关注重点 | 建议近期复查或重点监测的项目 |
| 后续预期 | 基于当前趋势的合理预期 |

- 分析完成后，结果写回 `analysis_sections`。
- `storage_status` 更新为 `analyzed`。
- 分析失败时，`storage_status` 可更新为 `analyze_failed`，并提供重新分析入口。

### FR-007 同日后续报告触发分析更新

- “同一自然日”以患者本地时区的 00:00-23:59 为准。
- 后台重跑可在执行时临时读取同一自然日内相关的检验、检查、病理、手术和其它报告，但不保存报告之间的分析引用关系。
- 若同一自然日已有分析结果，后续又有新报告入库，系统应判断新报告是否可能补充、验证或改变既有分析依据。
- 例如检查 A 先出结果并已完成分析，之后检查 B 上传；若 B 可验证 A 的异常指标或结论，A 的既有分析应标记为可能过期。
- 系统应把受影响的已分析报告标记为 `analysis_outdated=true`。
- 对于已经由用户触发过分析的报告，后续同日相关报告入库后，系统应在后台临时读取当日相关报告重新运行分析链路，并更新受影响报告的 `analysis_sections`。
- 新入库报告本身仍遵守“入库后确认分析”规则：该报告自己的首次分析由用户确认触发。
- 自动重跑失败时，旧分析仍可查看并保持可能过期状态；系统可在报告详情中提供手动重新分析入口。
- 若本次上传更新了报告数据或另存为新报告，则应重新评估对同日既有分析的影响；仅补充原始文件来源时不触发分析更新。

### FR-008 报告列表

- 报告场景应展示当前 `account` 下的报告列表。
- 默认按报告时间倒序排列。
- 列表项至少展示：
  - 报告类型
  - 报告时间
  - 解析或分析状态
  - 异常指标数量
- 已分析报告应有明确视觉标记。
- 无报告时展示：“还没有报告，上传一份试试。”
- 筛选无结果时展示：“没有符合条件的报告。”

### FR-009 筛选与排序

- 报告类型筛选支持：
  - 全部
  - 检验报告
  - 检查报告
  - 病理报告
  - 手术报告
  - 其它报告
- 时间范围筛选支持：
  - 近 1 月
  - 近 3 月
  - 近 6 月
  - 近 1 年
  - 全部
- 排序方向支持：
  - 时间倒序
  - 时间升序
- 筛选、排序和选中报告状态应在报告场景内保留。

### FR-010 单份报告详情

- 用户点击报告列表项后，展示报告详情。
- 报告详情至少包含：
  - 报告基本信息
  - 原始文件引用
  - 结构化数据
  - 分析结果
  - 检验报告趋势图
- 检验报告需逐项展示指标名称、结果原文、参考值原文和异常方向标记。
- 视觉解析模型根据结果原文和报告自身参考值判断方向：异常或偏高只显示 `↑`，偏低只显示 `↓`，无异常或无法判断时不显示标记。
- 方向判断在报告解析阶段完成；前端不计算，后端不另建复杂参考范围规则。
- 检查报告展示检查名称、检查时间、临床诊断、检查方法、检查表现、检查诊断或结论。
- 病理报告按送检标本、巨检、诊断、取材位置展示；缺失分类展示为空状态，不从其它分类内容推断补写。
- 手术报告按术前诊断、术中诊断、麻醉方法、开始时间、结束时间、是否输血、术中失血量、术中尿量、术中输血量、术中输液量、术中其他用药、手术经过、术后生命体征展示。
- 其它报告需展示报告名称和报告正文。
- 未分析报告展示“分析此报告”按钮。
- 已分析报告直接读取并展示已存分析结果。

### FR-011 检验报告历史对比与趋势图

- 历史趋势只覆盖检验报告中的指标。
- 检查、病理、手术和其它报告不生成趋势图，可在报告聊天中按原文进行对比。
- 若存在同类历史检验报告，应在指标旁展示与上次的变化方向。
- 变化方向至少包括：
  - 升高
  - 降低
  - 持平
- 趋势图默认展示当前报告中的异常指标。
- 用户可切换查看不同指标。
- 趋势图至少支持最近 5 次同类报告数据。
- 每个历史节点展示该次报告的 `result_text`、`reference_text` 和 `flag_text` 方向箭头。
- 后端可在查询趋势时临时从 `result_text` 生成绘图数据，但不得把临时解析出的数值、单位或参考上下限写回数据库。
- 只有同一指标的结果原文能够明确识别为数值且原始单位一致时才绘制折线；其它情况按时间顺序展示原始结果列表。
- 系统不执行复杂单位换算，不根据参考值原文重新计算异常状态。
- 前端渲染后端在 `GET /api/reports/{report_id}` 响应中按需返回的 `trend_data` 字段。

### FR-012 报告自然语言查询与上下文问答

- 用户可围绕当前选中报告提问，也可直接查询多份历史报告。
- 报告聊天复用 v0.1.0 的会话、消息、流式生成、分支、恢复和左侧历史导航能力。
- 会话记录沿用现有 `conversation_sessions` 结构。
- 对话中实际读取、修改、确认写入或分析的报告以消息级 `context_resources` 保存，并显示在聊天末尾的报告与文件索引中。
- 报告聊天界面为左侧聊天、右侧报告；右侧报告面板支持折叠和展开。
- 复杂自然语言查询可使用 `report-query` Skill 统一意图识别、证据读取和回答组织流程。
- 自然语言查询至少支持：
  - 最近一次或最近 N 次报告查询
  - 指定时间范围报告查询
  - 异常指标汇总
  - 单指标跨报告趋势
  - 两份或多份报告差异对比
  - 定性指标状态查询，例如阳性项、阴性转阳性
- 请求沿用现有会话消息接口并携带 `account`、`session_id` 和消息级 `context_resources`；对话实际使用某份报告后，对应消息资源包含该 `report_id`。
- 后端回答时应优先基于当前账号保存的指标名称、结果原文、参考值原文、异常方向箭头和已存分析结果。
- 查询需要访问报告数据库时，报告智能体（`ReportAgent`）发起受控证据读取工具调用；取得证据后由模型直接生成患者可读回答。
- 当前上下文已经包含完整证据时，报告智能体（`ReportAgent`）可直接回答。
- 当原始结果无法可靠解释或不能直接比较时，回答应展示原文并说明无法形成可靠趋势。
- 查询能力的验收关注自然语言意图覆盖、证据准确性和原文引用，不关注底层工具如何按业务查询类型拆分。
- 问答结果展示在报告场景左侧聊天区域；从首页直接发起且未打开报告面板的查询仍在首页展示。
- 报告场景快捷问题至少包括：
  - “这份报告最需要关注什么？”
  - “和上次比有什么变化？”
  - “接下来需要复查哪些项目？”
  - “这个指标偏高是什么意思？”

### FR-013 报告分析收藏

- 报告分析结果应提供收藏入口。
- 报告问答回答沿用 v0.1.0 的收藏入口。
- 收藏创建请求的 `source_type` 新增支持：
  - `report_analysis`
  - `report_qa`
- 收藏快照需保存收藏时的内容。
- 收藏详情可提供返回原报告或原对话的入口。
- 取消收藏不删除源报告、源分析或源对话。

### FR-014 报告修改与删除

- 用户可删除已上传的报告。
- 自然语言修改和删除请求可使用 `report-correction` Skill 统一目标定位、旧值读取、变更草稿和待确认动作创建流程。
- 删除报告时，系统必须同时删除：
  - `reports` 表中该报告的元数据记录
  - 对应报告子表（`lab_test_report`、`examination_report`、`pathology_report`、`surgery_report` 或 `other_report`）中的记录
  - 与该报告关联的源文件记录；若某个上传源文件不再被任何报告引用，再删除对应原始文件
- 删除报告不删除已生成的收藏快照；收藏详情返回原报告时发现报告不存在，应仅展示收藏快照。
- 用户可修改报告的基本信息（报告时间、报告类型）。
- 用户可通过自然语言修正检验报告中的结果原文、参考值原文和异常方向箭头。
- 结构化修正只影响 `reports.db` 中的解析结果。
- 指标修正前必须展示确认内容，至少包含目标报告、目标指标、原值、新值和用户原话。
- 写入结构化数据必须以用户确认且目标明确为前提。
- 用户确认后直接更新对应报告数据；待确认内容和确认结果保留在原有对话消息与 `pending_action` 中。
- 自然语言修正的验收关注是否生成正确的待确认变更、是否阻止未确认写入以及确认后是否正确更新，不关注底层工具如何按修改类型拆分。
- 修改报告基本信息后，若该报告已有分析结果，应提示用户是否重新分析。
- 删除和修改操作需二次确认。
- 删除和修改只允许操作当前 `account` 名下的报告。

### FR-015 重复报告处理

- 系统应在解析完成后生成业务指纹，用于识别“同一医学报告”的不同原始来源。
- 业务指纹至少参考当前 `account`、报告类型、报告时间或采样时间、可识别机构名、指标或检查项目集合、结果原文、参考值原文和异常方向箭头。
- 文件哈希完全一致时，应识别为已上传原始文件。
- 文件哈希不同但业务指纹高度一致时，应识别为疑似重复报告，例如电子网络截图和纸质扫描件。
- 疑似重复报告必须由用户确认处理方式。
- 首页重复报告确认卡片至少展示：
  - 已有报告的类型、时间、指标或条目数量、异常数量
  - 本次上传文件的来源摘要和解析预览
  - “作为补充文件保存”按钮
  - “用本次解析结果更新”按钮
  - “仍作为新报告保存”按钮
- 默认推荐操作是“作为补充文件保存”：只把本次原始文件关联到已有 `report_id`。
- 用户选择“用本次解析结果更新”时，必须展示结构化差异确认；确认后直接更新已有报告数据，并将已有分析标记为可能过期。
- 用户选择“仍作为新报告保存”时，才生成新的 `report_id` 并进入正常入库流程。
- 重复报告识别只在当前 `account` 范围内进行。

### FR-016 异步处理与中断恢复

- 报告解析和智能分析均为后台异步处理，不依赖前端页面保持打开。
- 用户在解析或分析进行中切换场景或关闭前端页面时，只要后端进程仍在运行，后端继续完成处理并写回结果。
- 用户重新进入报告场景时，已成功写入的报告和分析通过最新 `storage_status` 展示。
- 文件上传过程中网络中断，视为上传失败；前端应展示上传失败提示和重试入口，不生成报告记录。
- 批量上传中单个文件网络中断时，只将该文件标记为失败并允许单独重试。
- 上传失败不产生残留文件；若服务端已接收部分数据，应在超时后自动清理。
- 批量上传进度只保存在前后端运行时内存中，不写入 `reports.db`；任务达到终态后按 TTL 清理，应用或后端重启后不恢复失败批次。

### 10.6 上传流程展示

```text
用户点击上传 -> 选择一个或多个文件
    -> 前端逐文件展示“上传中...”，界面切回首页
    -> 每个文件上传完成后独立展示“解析中...”
    -> 解析完成，若疑似重复则展示重复报告确认卡片
    -> 用户选择补充文件、更新结构化数据或另存为新报告
    -> 无重复或重复处理完成后，展示入库确认卡片
    -> 用户点击“开始分析”
    -> 前端展示“分析中...”
    -> 分析完成，展示结构化分析结果
    -> 底部展示“查看该报告”跳转按钮
```

入库确认卡片至少包含：

```text
┌──────────────────────────────┐
│ 报告已入库                    │
│ 检验报告 · 2026-04-23         │
│ 共 12 项指标，其中 3 项异常    │
│                              │
│ [开始分析]    [暂不分析]       │
└──────────────────────────────┘
```

重复报告确认卡片至少包含：

```text
┌──────────────────────────────┐
│ 这份报告看起来已上传过        │
│ 已有：检验报告 · 2026-04-23   │
│ 共 12 项指标，其中 3 项异常    │
│ 本次：纸质扫描件 · 解析一致    │
│                              │
│ [作为补充文件保存]            │
│ [用本次解析结果更新]          │
│ [仍作为新报告保存]            │
└──────────────────────────────┘
```

### 10.7 异常指标配色

| 标记 | 颜色 | 说明 |
| --- | --- | --- |
| normal / 正常 | 默认文字色 | 报告未标记异常 |
| abnormal/high / `↑` | `#E67E22` | 异常或偏高只显示上箭头 |
| low / `↓` | `#3498DB` | 偏低只显示下箭头 |

### 10.8 业务规则补充

- 上传后自动触发解析。
- 解析超时阈值为 60 秒；超时后标记为 `parse_failed`。
- 解析失败不阻塞其它功能，原始文件保留，报告标记为 `parse_failed` 并允许重试。
- 同一医学报告重复上传时，系统应提示用户将新文件作为已有报告的补充来源、更新已有结构化数据，或确认另存为新报告。
- 分析必须在用户确认后才触发。
- 分析结果必须回写数据库，避免重复调用大模型。
- 用户可对已分析报告重新触发分析，重新分析结果覆盖旧结果。
- 同一自然日新报告入库后，若可能补充或验证已分析报告，应标记相关分析可能过期，并后台自动重跑受影响的既有分析。
- 从首页分析结果跳转到报告场景时，只改变当前选中报告。

## 11. 非功能要求

### 11.1 可用性

- 报告解读文案应面向患者，避免堆叠专业术语。
- 异常指标、风险信号和下一步建议应优先展示。
- 上传、解析、入库、分析和跳转都需要明确反馈。
- 报告详情应能让用户快速看到“哪些异常最重要”。

### 11.2 性能

- 上传开始后应立即展示反馈。
- 报告列表加载目标不超过 1 秒。
- 趋势图切换目标不超过 500ms。
- 多模态解析和智能分析可异步处理，但前端必须展示明确状态。

| 指标 | 目标 |
| --- | --- |
| 文件上传响应 | 20MB 以内不超过 3 秒进入处理中状态 |
| 多模态解析 | 单页报告目标不超过 30 秒 |
| 分析生成 | 目标不超过 20 秒 |
| 报告列表加载 | 目标不超过 1 秒 |
| 趋势图渲染 | 目标不超过 500ms |

### 11.3 可靠性

- 解析失败不删除原始文件。
- 分析失败不影响已入库报告查看。
- 网络中断后，用户重新进入报告场景仍可查看已入库报告。
- 重复上传同一医学报告时默认不生成新报告记录，需经用户确认后才可另存为新报告。

### 11.4 安全与隐私

- 报告文件、结构化结果和分析内容均按敏感健康信息处理。
- 所有报告数据必须绑定 `account`。
- 当前用户只能访问自己的报告。
- 前端不得仅依赖本地 `account` 判断权限。
- 后端需校验登录态与 `account` 的绑定关系。
- 报告原始文件路径不得暴露不必要的身份信息。
- 退出登录后不得继续展示上一位用户报告数据。

## 12. 验收标准

### 12.1 上传与解析验收

- 用户可上传 PDF、JPG、PNG、HEIC 格式报告。
- 用户可在单批中选择多个报告文件，第一版最多 20 个。
- 超过 20MB 或格式不支持时有明确提示。
- 上传后界面切回首页展示处理状态。
- 上传完成后自动进入解析。
- 每个文件独立处理；部分文件失败时，同批成功文件仍可完成入库。
- 报告文件由当前账号配置的 `vision_parse` 默认模型解析。
- 解析成功后报告结构化数据写入患者报告数据库。
- 入库完成后首页展示确认卡片。
- 解析失败时展示错误提示和重试入口。
- 上传相同文件时，系统识别已有源文件或已有报告关联。
- 上传同一医学报告的不同来源文件时，系统展示重复报告确认卡片。
- 用户选择“作为补充文件保存”后，报告详情可看到多个原始文件来源。
- 用户选择“仍作为新报告保存”后，才新增一条报告记录。

### 12.2 分析验收

- 报告入库后展示分析确认入口。
- 用户点击“开始分析”后才触发分析。
- 分析中有加载状态，不能重复提交。
- 分析结果按结构化板块展示。
- 分析结果写回数据库。
- 再次查看已分析报告时无需重新分析。
- 分析失败时可重新分析。
- 同一天先分析报告 A、后上传相关报告 B 时，系统能标记 A 的分析可能过期，并在后台自动重新生成受影响分析。
- 自动重跑完成后，A 的分析应使用当次临时读取的 A、B 等相关同日报告重新生成，但不保存这些报告之间的引用关系。
- 自动重跑失败时，A 的旧分析仍可查看，并保持分析可能过期状态。

### 12.3 报告场景验收

- 用户可进入报告场景查看当前患者报告列表。
- 报告列表支持类型筛选、时间范围筛选和排序切换。
- 用户点击报告后可查看详情。
- 检验报告详情展示指标名称、结果原文、参考值原文和 `↑`、`↓` 异常方向标记。
- 检查报告展示检查名称、检查时间、临床诊断、检查方法、检查表现、检查诊断或结论；其它报告展示报告名称、时间和完整原文。
- 病理报告详情仅按送检标本、巨检、诊断、取材位置四个结构化分类展示。
- 手术报告详情完整展示指定的十三个结构化分类；源报告未提供的字段允许为空。
- 异常指标有明显视觉区分。
- 未分析报告可从详情页触发分析。
- 已分析报告可展示已存分析结果。
- 只有检验报告生成趋势图，可展示至少最近 5 次同类报告数据；历史不足时有明确空状态。

### 12.4 报告问答验收

- 用户可围绕当前报告提问。
- 用户可不选中单份报告，直接询问最近报告、异常指标、跨报告趋势和多份报告对比。
- 打开报告聊天后，主工作区展示左侧聊天和右侧报告，右侧报告可以折叠和展开。
- 报告问答提交后保留在报告场景，回答显示在左侧聊天区域。
- 对话中实际读取、修改、确认写入或分析的报告显示在聊天末尾的报告与文件索引中，点击后可在右侧打开。
- 报告聊天沿用现有会话历史并显示在全局左侧导航栏；会话记录不增加报告专用字段。
- 回答内容基于当前账号的结构化报告数据、当前报告上下文或历史报告范围。
- 原始结果无法可靠解释或单位明显不一致时，回答展示原文并说明无法形成可靠趋势。
- 定性指标查询可返回阳性项、阴性项和状态变化。
- 快捷问题可填充输入框并正常提交。

### 12.5 收藏验收

- 用户可收藏报告分析结果。
- 用户可收藏报告问答回答。
- 收藏快照绑定 `account`。
- `我的收藏` 可展示报告类收藏。
- 收藏详情可查看快照内容。
- 取消收藏不删除原报告或原分析。

### 12.6 数据隔离验收

- 不同 `account` 的报告列表互不可见。
- 不同 `account` 的报告文件互不可访问。
- 退出登录后不展示上一位用户报告数据。
- 报告、分析和收藏均写入对应患者目录。

### 12.7 报告修改与删除验收

- 用户可删除已上传的报告。
- 删除前有二次确认。
- 删除后报告从列表消失，原始文件和结构化数据均被清除。
- 删除报告不影响已生成的收藏快照。
- 用户可修改报告的基本信息（报告时间、报告类型）。
- 用户可用自然语言修正指标原文，例如“ALT 不是 65 U/L，是 56 U/L”或“HBsAg 识别错了，是阴性”。
- 指标修正前展示确认卡片；用户确认前数据库不发生写入。
- 指标修正后报告详情展示新值，确认内容和结果可在原有对话中查看。
- 修改已分析报告时提示是否重新分析。
- 只能操作当前 `account` 名下的报告。

### 12.8 异步处理验收

- 用户在解析或分析进行中切换场景或关闭页面，后端继续处理。
- 用户重新进入报告场景时，能看到后台已完成的解析或分析结果。
- 文件上传过程中网络中断，展示上传失败提示和重试入口。
- 上传失败不产生残留报告记录。

### 12.9 报告智能体、Skill 与工具边界验收

- 调用轨迹能够区分模型推理、Skill 执行、工具调用和后端服务写入。
- 当前上下文已包含完整报告证据时，报告智能体（`ReportAgent`）直接生成解释或分析，并将本次生成记录为模型推理节点。
- 问题需要访问历史报告或趋势数据时，报告智能体（`ReportAgent`）通过受控证据读取工具取得当前 `account` 的数据，再生成回答。
- 自然语言修改和删除请求可生成结构化变更草稿并创建 `pending_action`；用户确认前目标报告数据保持原值。
- 报告分割、重复识别、同日分析失效判断、后台任务触发和确认写入能够独立于 Skill 执行，由后端服务规则决定结果。
- 简单列表、详情和状态查询可直接通过业务接口完成。

## 14. 风险与待确认项

### 14.1 风险

| 风险 | 影响 | 缓解措施 |
| --- | --- | --- |
| 报告格式差异大 | 解析准确率不稳定 | 优先支持常见体检和医院报告格式 |
| 多模态解析耗时长 | 用户等待体验差 | 异步处理、状态反馈、失败重试 |
| 指标单位不统一 | 趋势对比可能误导 | 保留结果原文，不做单位换算；无法可靠生成折线时改为按时间展示原始结果列表 |
| 报告自身参考值缺失或条件不明确 | 异常判断可能误导 | 只展示报告原文，不推断或重新计算异常状态 |
| 同一报告多来源重复上传 | 报告列表、趋势和分析被重复数据污染 | 解析后业务指纹判重，默认关联为已有报告的补充文件，另存新报告必须由用户确认 |
| 自然语言修改误识别 | 可能改错报告或指标 | 写入前必须确认，目标不明确时先追问 |
| 历史数据不足 | 趋势图无法完整展示 | 提供“暂无足够历史数据”空状态 |
| 分析结果过度医疗化 | 用户误解为诊断 | 文案强调辅助理解和就医建议 |

### 14.2 已确认实现口径

- 报告图片和 PDF 使用当前账号的 `vision_parse` 默认模型解析。
- 检验指标首次出现且无法匹配现有字典时自动收录为 `pending`。
- 检验结果和参考值只保存报告原始文本；视觉解析模型判断异常或偏高时保存 `↑`，偏低时保存 `↓`，无异常或无法判断时保存空值。
- 检查报告结构化保存检查名称、检查时间、临床诊断、检查方法、检查表现、检查诊断或结论；其它报告保存报告名称、时间和完整原文。
- 趋势图只覆盖检验报告。
- 参考值只采用报告自身原文，不建立复杂参考范围规则库。
- 报告聊天复用现有会话和消息接口，通过消息级报告引用恢复右侧报告和文件索引。

## 15. 结论

v0.2.0 只聚焦报告场景，是在 v0.1.0 的登录、首页对话和收藏闭环上新增报告能力的版本。该版本的交付重点是让患者可以完成“上传报告 → 结构化入库 → 自然语言查询与对比 → 确认修正结构化数据 → 确认分析 → 围绕报告追问 → 收藏重要结果”的完整报告对话闭环。
